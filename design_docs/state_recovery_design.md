# 引擎保存恢复与旧服务记录

设计日期：2026-10-24。清理日期：2026-10-26。

当前保留 `simulator/state_snapshot.py`、`simulator/state_store.py` 及引擎级测试。旧开发者会话和旧多人 HTTP 服务的持久化适配、浏览器恢复检查与专用测试已移除；旧 SQLite 文件未删除。

现用入口为每次开服重置的 [真人房间](hosting_design.md) 和 [人机试玩](bot_play_design.md)，均不载入旧存档。下文涉及旧会话、房间注册表和强杀重启的勾选属于历史验收，不表示当前服务提供重启恢复。个人断线暂停与托管以当前开服设计为准。

## 1. 恢复目标与不恢复的情况

需要恢复：后端进程重启、运行后端的电脑断网或重启后，能继续原来的游戏，不重新洗牌、发牌、改变手牌顺序或重复结算。

不恢复：服务器已确认房主个人掉线而销毁的房间、房主显式关闭的房间，以及管理员明确终止的房间。关闭记录也要持久化，不能启动时把旧快照复活。

管理员只是关闭网页不算服务器故障。服务器故障恢复与个人断线 300 秒是不同流程：停服期间不消耗游戏剩余时间，不消耗个人宽限，不批量补打牌。

服务器全局故障恢复后，房间先处于恢复保护态，而不是因为原房主的 WS 都不存在，就立刻套用“房主个人掉线直接删房”。具体恢复等候期限和故障归因阈值仍在联机文档中待确认。

## 2. 先做两层，不一次重写整个服务器

### 第一层：GameState 完整保存与恢复

先独立于房间、网络和 UI 实现：

- ✅ 把当前 GameState 转为完整、版本化、可校验的私有存档。
- ✅ 从存档重建等价状态，保留实体牌、分组、各类窗口及结算记录。
- ✅ 用新的单调时钟基准恢复剩余操作时间，验证 t1/t2/t3/t4 均不被重置。
- ✅ 使用 SQLite 原子保存和加载，测试实际关闭并重开数据库、独立进程恢复及损坏存档拒绝。
- ✅ 在恢复后的引擎继续执行动作，跑到正确结算和下一局，而不是只验证 JSON 长得相同。

第一层是保留的引擎能力。旧本地会话自动存档和真实 HTTP 服务强杀重启测试已随旧服务移除。

### 第二层：运行会话与自动保存（历史实现，已移除）

在核心格式稳定后再接运行入口：

- ✅ 本地开发者会话保存模式、计时配置、轮次、修订号、阶段记录及 bot 等待剩余量；恢复后手动继续或放弃。
- ✅ 本地多人房间保存最多十名成员、身份验证摘要、密码哈希、房主、本局/下局四席安排、座位分数、观战角色和权限。
- ✅ 本地注册表原子保存 `identity -> active_room`、随机凭证摘要和成功命令缓存；同一凭证重启后不重复占房，不能凭同名冒领。不会保存明文凭证或明文房间密码。
- ❌ 正式网络的断线宽限、托管和跨设备恢复码尚未实现；本地身份仍依赖原窗口 `sessionStorage`，不是自然人防多开。
- ✅ 本地运行层将保存嵌入命令与 timer tick 的串行处理，收到成功确认的动作已经落盘；失败退回最后提交状态并暂停，不返回成功。
- ✅ 本地多人 `command_id` 与房间/身份同事务提交；服务实例 ID 阻止重启前的迟到请求作用到恢复后的窗口。正式 WS 连接交接仍未接入。
- ✅ 底层存储提供终止墓碑和版本检查，已测试服务重开后不可复活。
- ✅ 本地房主显式关房与释放成员归属原子保存，重启不可复活；同名新房使用新 ID。
- ❌ 房主个人掉线判定及自动关房尚未实现，不把“重启后原连接不存在”视为房主个人掉线。

核心、开发者会话和本地房间注册表有独立类型/版本校验，不能把带可编辑牌堆的开发者会话当作多人房间载入。

### 旧本地多人恢复规则（历史记录）

旧多人服务曾加载端口对应的私有 SQLite 文件。该入口现已移除；以下描述其原恢复合同。

- 原四个参赛身份和原房主都用原凭证访问过恢复房间后，才允许原房主点击“继续对局”。房主若观战，需要五个身份；其他观众不阻塞恢复。未开局/已结算/安排阶段正常重启直接返回原阶段。
- 恢复等待无自动时限，不修改游戏倒计时。暂停期间禁止出牌、整理、改座位、观战切换和读牌山；房主仍可主动关房。继续时只平移冻结的游戏时钟，t4 内部暂停的 t3 仍按原规则处理。
- “已返回”只记录本次恢复中原凭证访问过，不代表持续在线；本轮无心跳、无个人断线识别、无 300 秒宽限。再次重启重新确认返回情况。
- 刷新原窗口保留凭证；关闭标签页/清除数据可能丢失凭证。相同用户名、IP 或房间密码不能替代原凭证；本轮不提供恢复码或跨设备找回。
- 候场、赛后查看和安排阶段不自动重开局、轮庄或改分；恢复的牌山记录仍只在 `REVIEWING` 可查询。
- 磁盘写入失败返回 503，不确认新动作；退回最后成功提交的注册表并冻结房间。修复磁盘后仍须原身份返回、房主手动继续。损坏/不兼容文件启动时直接拒绝，不覆盖成空房间。
- 同一个数据库只供一个服务进程使用；当前没有多 worker/多机存储协调，也不声称已解决服务器网络故障归因。

## 3. 不使用公开快照当存档

`GameState.to_public_dict(...)` 是为客户端过滤后的视图，不包含其他人的私牌、完整牌山及全部未裁决状态，不足以恢复整局。

新增存档属于服务器私有数据，不通过公开状态、错误响应、静态目录、下载接口或观战视图返回。不能把完整存档发给浏览器后再用 CSS 遮挡。

建议使用显式 JSON 数据合同和类型重建，不使用 pickle，不从存档中的模块名/类名动态导入执行对象，不上传任意 Python 对象恢复。

存档顶层至少包含：

| 内容 | 用途 |
| --- | --- |
| `schema_version`、存档类型 | 检测格式兼容性，区分核心、开发者会话、正式房间 |
| 存档 ID、状态版本 | 标识保存点，防止旧写覆盖新写 |
| 游戏/局 ID、保存时间 | 恢复身份与排错；墙钟保存时间不直接参与补跑超时 |
| 规则集/计算器与结算器版本标识 | 只从服务器允许的工厂或注入对象恢复，禁止自行导入 |
| 全量 GameState 数据 | 真正可以继续运行的状态，而非展示摘要 |
| 相对计时状态 | 与旧进程的绝对单调时钟脱钩 |
| 可选会话/房间元数据 | 由运行层管理，不污染规则引擎 |

格式版本不兼容、未知枚举、非法牌值、悬空牌 ID、重复 ID、错乱的组/席位绑定或损坏结算记录，应明确拒绝恢复，不能静默删字段、重发牌或随机生成新的实体 ID 来“修好”。

## 4. 核心需要保存的完整内容

| 分类 | 必须保留 |
| --- | --- |
| 身份/阶段 | `game_id`、`round_id`、phase、庄家、当前席、规则配置、计时配置 |
| 牌山 | 剩余牌的完整物理抽取顺序，不只是张数；恢复后下一张必须相同 |
| 四家 | 玩家/座位信息、累计分数、手牌牌值与稳定 ID、视觉顺序、分组 ID/成员/顺序、散牌顺序、副露与朝向、各家弃牌 |
| t1 | 最近弃牌、窗口 ID、来源、全部合法选项、已提交请求及请求 ID、自动过集合、状态、剩余时间 |
| t2 | 执行者、来源牌、吃法候选与选择模式、detail ID、原响应窗口引用、剩余时间 |
| t3 | turn window ID、本次摸牌 ID、本人操作选项、胡/杠提示是否已过、剩余时间 |
| t4 | 预备加杠 payload、待移除实体 ID、合法抢杠者、已提交请求、窗口 ID、原 t3 窗口、t4 剩余时间和内部暂停的 t3 剩余时间 |
| 历史/结算 | 弃牌历史、日志的私有标记、已裁决动作、SettlementEvent、RoundResult、已有分数变化和结算 ID |

规则适配器、计番对象、锁、数据库连接、线程、Socket 和浏览器对象不直接序列化。RuleAdapter/ScoringAdapter 由服务器认可的版本注册或显式注入重建；不因恢复而重新评估并改写已完成的结算。

当前记录并核对 Adapter 类型、`ruleset_id` 和内置判胡的 `min_fan`；自定义 Adapter 必须显式注入匹配实例，不按文件内容动态导入。修改计算器规则时需主动更换规则版本标识；当前不会自动对源代码作语义差异检测。

旧记录保留原结算结果，恢复不会重算并改写历史分数。未来联机服务应通过服务器认可的规则版本配置决定是否允许旧局继续，不偷偷按新番种解释旧存档。

## 5. 计时的保存和恢复

- 保存的是该检查点的剩余量、原时长与必要的窗口状态，不依赖进程旧 `time.monotonic()` 数值。
- 无计时仍保存为无计时，不能因为恢复而自动打开默认 5 秒或 30 秒。
- 加载存档不自动调用发牌、摸牌、过牌、超时、结算或下一局。
- 恢复等待期间保持冻结；真正恢复游戏时才用新时钟重建 deadline。不能加载后先让 deadline 自己过期，再等房主点击恢复。
- 同一阶段已经提交的响应保留；t1 剩 2 秒就继续等 2 秒，不重新给 5 秒，也不因为请求都在就提前跳过。
- t4 有两层时间：正在运行的 t4 和本来已暂停的 t3。内部 t3 应按加杠声明暂停点保存，不能按当前保存时刻继续扣它的时间。
- t4 全过后完成加杠、补摸一次并恢复原 t3 剩余时间；抢杠胡后只结算一次，不额外补摸。
- 个人失联、服务恢复和 t4 的暂停原因可能嵌套，恢复其中一个原因不代表解除其他暂停。
- 日志中的历史时间是审计信息，不应被误当作新的截止时间。需要比较的请求时间和窗口时间应按合同转换，不能混用新旧进程的时钟。

保存点由运行层串行选定。若当前已经到期，应先按正常运行规则处理到期，再保存稳定的新状态；不能一边保存一边有另一个线程改变手牌。

## 6. 落盘和崩溃一致性

建议使用 Python 标准库 `sqlite3`：它可以管理本地磁盘数据库，不需要额外运行数据库服务。[Python 官方文档](https://docs.python.org/3.13/library/sqlite3.html)

第一层提供存储接口和稳定的检查点记录；接入会话后，正常动作路径应是：

```text
验证身份和当前窗口
  -> 串行执行动作/超时推进
  -> 校验新状态
  -> 同一事务保存新状态、命令结果、去重及必要结算/归档
  -> 事务成功
  -> 才对客户端确认成功并推送
```

- 保存失败不能照常返回成功。要么回到上一提交状态，要么冻结会话并明确报错，不能继续在未落盘的新状态上玩。
- 中途崩溃后只恢复最后一次完整提交；不能存在新分数配旧手牌、已补摸但窗口仍是补摸前等混合状态。
- 相同 `command_id` 的成功结果与状态一起保存；成功确认丢在网络上时，重试不能重复执行。
- 恢复时保留结算 ID，不通过重新算一次结算来“还原分数”。已经开始下一局也不能再次给上一局扣分。
- 房间终止和释放身份占位也要原子保存。终止记录覆盖旧的可恢复检查点。
- 后端数据目录放在非静态目录，加入 git 忽略，限制访问；私牌、密码哈希和会话摘要不进入普通调试日志。
- 磁盘损坏或最后一次提交无法可靠读取时，应失败并报告；不能静默退回旧快照又声称所有已确认动作都还在。

原子事务只保证提交的一致性；实际主机掉电下的耐久性还依赖数据库设置、磁盘及备份。实现时选择明确的耐久配置并实测，不以“调用了写文件”替代故障验收。

当前 SQLite 使用完整同步提交。每次游戏修改保存，运行期间的纯倒计时约每秒补一次检查点；非正常结束恢复最近一次成功保存的时间，纯倒计时可能回退约一个检查点周期，另加调度/写盘延迟。正常 Ctrl+C 会额外保存当前剩余时间。已经成功确认的出牌、分组和结算不会仅因没有等到一秒周期而丢失。

## 7. 结算后查看牌山顺序

用户已确认：进行中的上帝视角看不到牌山顺序；正常结算后允许复盘看这一局的牌山顺序。

最新确认并已实现的查看窗口：正常结算进入房间 `REVIEWING`，所有当前房间成员（参赛者、公共/上帝观众、房主）都可分别点击桌面牌山查看。没有自动倒计时，也不要求全员确认。房主点击“下一局”提交 `prepare_next_round` 后，全房进入 `ARRANGING`，关闭查看弹窗和牌山查询权限，再安排四个座位。保存座位或关闭安排面板不会洗牌、发牌、轮庄或改变分数；房主最终“确认开局”才调用引擎开始下一局。普通成员不能跳阶段或代替房主确认。

需要从新局洗牌后、发牌前开始记录，不能只在结算时保存剩余牌山：

- ✅ 本地房间在洗牌后、发牌前记录完整初始牌序，按实际抽取先后展示，不直接展示内部 `pop()` 反向数组。
- ✅ 区分起手发牌、正常摸牌、三种杠后补牌及最终剩余部分，记录取牌位置与席位。
- ✅ 记录绑定固定 `round_id`、规则版本、轮次和当局名字/座位，不因下一局换人改写旧记录。
- ✅ 正常 `ROUND_ENDED` 且已有 `RoundResult`、房间仍在 `REVIEWING` 时才允许读取；房主和上帝观众也不能提前绕过。成功结算与牌序记录同事务落盘。
- ✅ 新局不覆盖旧的私有记录；安排阶段和新局均不能通过旧 round ID 查询，更不会泄漏新局牌序。首版没有历史记录下载入口。
- ✅ 查询校验身份、当前房间、当前结算局及阶段；被踢者、其他房间及未知会话不能仅凭 round ID 下载。
- ✅ 牌序记录与完整房间注册表同事务持久化，重启后恢复查看阶段及原始取牌顺序，仍保持原查询权限。

实现位于 `multiplayer/round_review.py`。通过引擎已有的 RNG 注入点捕获洗牌完成后的原始数组，不修改 `GameState`、`TileWall` 或真人/bot 动作合同；随后从实际发牌/摸牌/补牌事件增量标注记录，并核对剩余牌山是否仍匹配。日常状态只带阶段及可用性标记，不附牌序；点击后才请求独立的 `GET /api/local/wall-record?room_id=...&round_id=...`。前端在阶段切换时清除弹窗内容并丢弃迟到响应。已经看过或另行保存的旧局数据无法撤回，保密重点是新局牌山始终不提前下发。

现有 `TileWall` 的剩余牌、弃牌日志和当前手牌，不必然能反推出完整的初始发/摸顺序。对已经开过且从未记录初始牌序的旧局，只能标记“无完整牌序记录”，不能编造历史。

第一步只承诺记录与只读查询所需数据；完整逐步动画、回退操作、按人浏览全部历史手牌等回放功能，不与“能看牌山顺序”混为一个已完成功能。

## 8. 当前保留的实现

```text
simulator/state_snapshot.py    完整引擎快照与恢复
simulator/state_store.py       私有 SQLite 原子存储
test/test_state_snapshot.py    窗口、计时、实体牌与结算往返
test/test_state_store.py       数据库、进程恢复与损坏检查
multiplayer/round_review.py    当前房间的赛后牌山记录
multiplayer/test/test_round_review.py  赛后记录与局间边界
```

核心入口为 `capture_game_state(game, now=...)` / `restore_game_state(snapshot, now=...)`，属于私有数据接口。当前牌山 HTTP 合同在 `multiplayer/test/test_web.py` 检查。

旧会话、房间注册表持久化及专用检查已移除。今后若重新提供重启恢复，需要接入并验收，不能按历史记录认定当前服务已具备该功能。

## 9. 必要测试（包含旧服务的历史验收）

- ✅ 各稳定 phase 保存再恢复，ID、分数、牌山下一张、手牌顺序和分组一致。
- ✅ 重复牌、单张组与跨组移动后，恢复仍能精确处理同一个实体牌。
- ✅ t1 已有部分/全部响应、计时 t1 必须等待剩余时间、关闭 t1 必须等未提交的真人。
- ✅ t2 两种吃法模式、恢复后不重复移牌和旧 detail ID 失效；其他非法选择仍由原引擎回归覆盖。
- ✅ t3 剩余时间、本次摸牌 ID、胡/杠提示状态保存；最后牌山不能杠仍由原引擎测试覆盖。
- ✅ t4 剩余时间与嵌套暂停 t3，全部过只补摸一次、抢杠只结算一次。
- ✅ 胡牌结算后、流局后、开始下一局后恢复，分数及庄家不重复变化。
