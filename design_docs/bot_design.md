## 1. 判断与方向

当前目标是**能和人玩、打法有可辨认差异且行为自然的 bot**。速度、大牌意愿、防守和牵制都是可选偏好；不只按平均收益或最强策略验收。✅ 已有独立风格配置、共享可见信息分析与轨迹说明；❌ 真人体验仍需接入后测试。P3 搜索保留为研究分支，P4 可学习这些风格，并保留显式风格条件。

保留这个核心接口：

```python
class Bot:
    def act(self, observation, legal_actions):
        """从本次 legal_actions 中返回一个具体动作。"""
        ...
```

数学规则、概率搜索、神经网络、训练得到的平均策略，都实现这个接口。训练器、牌局调度、计时、记录、存档和 UI 放在接口外面。

推荐顺序：**决策接口与无 UI 环境 → 可复现基线与评测 → 数学 bot → 初级风格与可玩性 → 按需学习/搜索增强**。P3 已有的采样搜索保留用于对照。CFR/MCCFR 保留为独立研究路线，不作为陪玩策略的依赖。

数学方法和神经网络可以组合：数学分析产生候选特征、搜索产生教师数据，网络近似昂贵的评估，必要时再进行有限预算搜索。没有必要一开始就选定唯一算法。

已补充要求：**Arena 从第一版同时支持快速跑局与有限时跑局，bot 计算始终有独立上限。** 不能以“离线训练不计时”为由允许 bot 无限计算，也不能将限时执行留到真人接入后才验证。

部分旧辅助模块仍有旧版牌数描述。新分析器以当前 `RuleAdapter`、判胡器和测试约定为依据，不从旧注释复制规则。

## 3. 边界：保留真人路径，Bot 通过独立适配接入

已确认约束：**Bot 增强为旁路新增，现有真人路径保持兼容；未经用户单独确认，不改变真人交互语义。** 本文对候选去重、全量吃法、自动确认等约定仅适用于 bot。

```text
真人 UI ──→ 现有真人操作接口 ───────────────────────────→ GameState

                                   ┌─ 只读观察与具体候选
GameState ──→ bots 中的适配层 ───────┤
                                   └─ Bot.act(obs, legal)
                                              │
                              bots.common_bot_helper.decision_driver ──→ GameState

Arena / UI / 房间运行层：调度、座位控制权、计时、串行提交与记录
```

- `GameState` 决定动作是否合法，以及执行后发生什么。
- `bots/common_bot_helper/observation.py`、`bots/common_bot_helper/decision.py` 和 `bots/common_bot_helper/decision_driver.py` 属于模拟器外部的 bot 适配层，负责观察、候选及命令映射。
- 策略的 `act()` 不拿到 `GameState`、规则引擎内部对象或可变状态引用，也不直接调用其修改方法。适配层由可信运行器调用，可以读取引擎和提交命令；它与策略实现的权限不同。
- Arena 负责离线四席调度、自动摸牌、推进流程、记录和结算。实时 UI/房间保留自己的真人命令路径，仅对明确配置的 bot 座位接入适配层。
- 训练器可以管理完整模拟状态，但给各席策略的输入仍必须通过同一观察投影。

### ✅ 3.1 模块归属与单向依赖

将三个适配文件放入 `bots/common_bot_helper/`，保留独立模块，不合并成一个大文件。这里的 `bots/` 同时承载策略接口、策略实现及其模拟器适配，不代表每个文件都只能包含纯策略。

依赖方向为 `bots → simulator / calculator_base`、`arena → bots / simulator`；实时运行层在需要 bot 时调用 `bots`。`simulator` 不导入 `bots`、`arena` 或训练框架，也不按 bot 类型分支改变规则。加载模拟器或启动纯真人服务，不应触发模型加载、训练任务或神经网络依赖的导入。

通用规则判定仍由现有模拟器/计算器提供。全量吃法、训练特征、听牌评分等先在 bot 层组合已有规则能力。以后确需抽取双方共用的纯规则函数时，必须保持原入口的返回合同和执行语义，并以已有真人测试验证兼容；不因它被 bot 使用就把整个适配层塞进模拟器。

### 3.2 真人与 Bot 的操作合同

✅ 已完成独立 bot 适配，原真人操作路径继续使用原合同。❌ 下表中实时人机混打的联调和浏览器验收尚未完成。

| 内容 | 真人路径 | Bot 路径 |
| --- | --- | --- |
| 吃法 | 沿用不超过五种列出、超过五种手选，以及原 t1/t2 流程 | 枚举全部具体吃法，映射回现有 listed/manual 执行入口 |
| 出牌 | 按玩家指定的实体牌 ID 出牌，同值牌也保留区别 | 可按牌值去重决策，由 driver 绑定自己座位的实体牌 |
| 胡/杠提示的“过” | 由玩家显式操作，或按原计时规则超时处理 | 选择出牌时，driver 仅为该 bot 座位按需确认提示 |
| 排序、拖动、分组 | 保留原交互、实体身份、移牌及选牌优先级 | 策略无需模拟 UI 整理；其编码不要求真人手牌规范化 |
| 计时 | 沿用开局设置及 t1～t4 语义，包含人机混打 | Arena 支持快速和有限时模式；两种模式下 bot 都有计算上限，实时 bot 同样受当前对局计时约束 |
| 超时/失败 | 继续执行现有真人超时规则 | 运行层对 bot 超时或故障按约定降级，并作废迟到结果 |

不把真人请求转发给 `decision_driver`，不要求真人客户端提交 `BotAction`，也不把 bot 观察投影替换为真人 UI 快照。引擎内已有的合法性、窗口和超时检查继续同时保护两条路径。

### 3.3 控制权与计算并发

- ✅ 离线 driver 的 HUMAN/BOT 控制权、代次和失效请求校验。
- ✅ Arena 的独立计算进程、有限时调度、迟到结果拒绝和故障回收。
- ❌ 在真实 UI/房间运行层接入上述机制，并验证真人操作与后台计时不被慢 bot 阻塞。

运行层维护权威的“座位 → HUMAN/BOT 控制权”及控制权代次。driver 在建立请求和提交结果时都要检查目标仍由相同 bot 控制；纯 Arena 显式将四席配置为 BOT，实时房间按自己的身份/托管规则配置。不能由策略传入一个 `player_id` 就取得操作权，也不能仅依赖用于展示的 `is_human` 字段。

交回真人、切换 bot、开始新局、暂停或恢复时，取消/作废此前请求。结果提交时重新校验局 ID、适用的 t1/t2/t3/t4 窗口、控制权代次、期限和相关候选状态。即使窗口 ID 尚未变化，已归还真人的座位也不能被旧 bot 结果操作。

实时运行采用“锁内生成脱离引擎的请求 → 锁外计算 → 锁内重新校验并提交”。工作线程/进程只返回决策，不直接修改房间。当前 UI 服务在持有会话锁时调用 tick/dispatch，将来接入不能直接在其中同步运行耗时的 `act()`。

计算期间真人依法可进行的拖动、分组、响应及出牌应继续可用，后台计时照常推进。校验关注本次决策相关状态，不因另一个座位整理了手牌就盲目用全局 revision 拒绝所有结果。任务队列和计算资源有上限，超时不阻塞后续真人请求；普通超时降级也仅作用于 bot 座位。

### 3.4 分开验收

P0/P1 首先完成独立 Arena，包含有限时执行与超时降级。真人 UI 和房间接入是后续独立工作；Arena 跑通不等于人机混打兼容已经完成。接入验收同时覆盖原真人路径、真实浏览器交互、计时和慢 bot 并发场景，详见第 12 节。

先不引入 Gymnasium、PettingZoo 或 OpenSpiel 作为核心依赖。先做匹配现有状态机的 Python 接口；需要接具体训练框架时再做薄包装。

## ✅ 4. 最小接口合同

P0 已实现下列核心合同；完整字段见 `bots/common_bot_helper/observation.py` 和 `bots/common_bot_helper/decision.py`：

```python
@dataclass(frozen=True)
class BotAction:
    action_id: str
    action_type: ActionType
    tile: TileValue | None = None
    required_values: tuple[TileValue, ...] = ()
    meld_index: int | None = None


@dataclass(frozen=True)
class DecisionRequest:
    decision_id: str
    player_id: str
    observation: Observation
    legal_actions: tuple[BotAction, ...]


class Bot(Protocol):
    def act(
        self,
        observation: Observation,
        legal_actions: tuple[BotAction, ...],
    ) -> BotAction:
        ...
```

约定：

1. bot 返回本次候选中的一个动作，不能自行拼接执行 payload。运行器同时验证决策标识、候选标识及语义，拒绝旧动作。
2. `action_id` 只在对应决策请求内有效。候选的语义顺序和编码必须稳定，不能依赖 UUID 或 Python 集合遍历顺序。
3. 引擎窗口 ID、实体牌 ID、UI 的 `option_id` 及实际执行参数由 bot 适配层保留映射。模型不学习这些偶然标识，真人仍按原实体 ID/选项合同操作。
4. 观察及候选中的嵌套内容也应不可变或复制隔离；仅使用 `frozen=True` 不能保证内部列表不被修改。
5. 每席一个独立 bot 实例及 RNG；避免自对弈的四份策略通过共享可变记忆交换私牌。模型的只读权重可以共享。
6. 第一版每局新建 bot 实例；跨局对手建模、显式 `reset()`、可恢复的循环网络状态等在确实需要时扩展。不要强迫所有 bot 实现训练生命周期。
7. 非行动时不调用 `act()`；空候选表示投影或调度错误。只有一个强制候选时运行器可直接执行，并在记录中标明。
8. `observation.decision_context` 提供本次剩余计算预算，供数学/搜索策略主动停止并返回当前最佳候选；具体字段在 P0 固定。预算属于运行上下文，默认不输入牌力网络。运行器独立强制执行期限，不能只相信 bot 自己看时间；`act()` 仍保留两个参数。

`Observation` 带有观察版本、规则标识和决策阶段。规则配置还要包含起胡门槛等影响合法性的参数；只记录 `ruleset_id` 字符串并不足以区分所有实验。

## ✅ 5. Observation：玩家有权知道什么（Bot 存档扩展未实现）

### ✅ 5.1 允许的输入

| 类别 | 内容 |
| --- | --- |
| 本人信息 | 自己的手牌计数、本次自己的摸牌、自己的副露，以及本人有权知道的历史 |
| 牌桌信息 | 庄家、当前行动席、各席分数、对手暗手张数、公开副露、各家当前弃牌、牌山剩余张数 |
| 历史 | 有顺序的公开摸牌事件（无别人摸到的值）、出牌、已完成吃碰杠及结算；本人的私有观察和动作历史 |
| 当前决策 | 决策阶段、来源玩家、相关弃牌或待加杠牌、本人候选需要的语义信息 |
| 规则 | 牌池、起胡条件、一炮多响开关、规则与结算版本 |

优先采用相对座位：本人、下家、对家、上家。底层保留真实席位映射供执行和调试，特征编码使用相对席位。牌值到整数索引使用显式固定表，不能直接迭代 `ALL_TILES` 集合。

计时/计算预算属于决策上下文；训练默认不把真实时间、网络延迟或 UUID 作为牌力特征。UI 手牌视觉顺序和私有分组不是胡牌规则的一部分，数学及网络特征默认使用牌值计数。

### ✅ 5.2 不允许的输入

不包含别人的未公开手牌、别人摸入的牌值、未来牌山顺序、发牌种子、私有快照、其他席位的合法候选、未裁决响应意向、提交状态或自动过名单。

不直接使用 `to_public_dict()` 作为 bot 输入。目前该方法仍有面向调试的开关，原始事件里也存在 `response_submitted` 等信息；现有过滤不能替代 bot 合同。采用显式白名单构造，不能只删除 `hand_tiles`。

副露公开到什么程度遵循游戏实际公开语义，而不是按“暗杠”名称推断。当前暗杠记录及 UI 展示能识别牌值；观察层应与确认后的展示规则一致。将来修改公开规则时同步升级观察版本。

### 5.3 历史、记忆和信息集

- ✅ 从开局维护各席可见的公开历史、自家起手牌、摸牌和动作历史；中途接入仅提供当前手牌引导，不补造此前私有历史。
- ❌ 有记忆策略、完整 CFR 信息集训练及 bot 历史/RNG/记忆的存档恢复。

仅有当前手牌和弃牌区不能表达完整历史：被吃碰杠的弃牌会从当前弃牌区移走，自己曾经摸入又打出的牌也不在当前手牌中。

环境从开局起维护经过过滤的公开历史，以及每席自己的私有历史。当前 `tile_drawn` 日志不记录摸牌值，运行器需在摸牌返回时为本人记录，不能事后从别人的状态补给策略。日志使用玩家可见的连续顺序，不暴露隐藏事件造成的原始序号空洞。

第一版数学 bot 可以只使用其中一部分。需要记忆的网络可以读取历史或维护私有状态；CFR 信息集则需要保留对应的可观测历史。若压缩、截断或合并历史，明确这是算法抽象，不宣称仍有完美记忆。

后续要从存档精确恢复有记忆的 bot 时，还需保存运行器维护的历史、bot RNG 和必要记忆。已有 `GameState` 存档不会自动包含这些新增内容；第一版先保证从头运行的实验可复现。

### ✅ 5.4 信息隔离检查

构造两个对某玩家具有相同可见历史、但对手暗手或剩余牌山排列不同的有效状态；该玩家的观察和候选语义必须相同。随机标识不参与语义比较。

同一 t1/t4 内改变其他人的提交顺序或已提交意向，也不得改变该玩家得到的信息。测量 bot 时，不能因为它与引擎运行在同一进程，就绕过这个边界。

## ✅ 6. Legal actions：把 UI 选项变成可执行候选

### ✅ 6.1 保留实际决策阶段

第一版保留引擎的两阶段吃牌流程，避免引入“先替 bot 缓存吃法、等裁决后偷偷执行”的隐含动作。

| 阶段 | bot 可见动作 | 运行器负责 |
| --- | --- | --- |
| `WAITING_DRAW` | 无策略决策 | 自动调用 `draw_tile()`，处理空牌山 |
| t3：`WAITING_TURN_ACTION` | 每个不同牌值的 DISCARD、每个具体暗杠/加杠、合法 HU | 候选绑定实体牌及引擎选项，调用现有执行入口 |
| t1：`WAITING_RESPONSE` | HU、明杠、碰、吃声明、PASS | 独立收集各席意向，交给引擎裁决 |
| t2：`WAITING_ACTION_DETAIL` | 每一种具体吃法、PASS | 把吃法映射为 listed 选项或三个实体牌 ID |
| t4：`WAITING_ROB_KONG` | HU、PASS，仅合格且未提交的席位 | 提交抢杠响应，保留现有结算/恢复 t3 行为 |
| `ROUND_ENDED` | 无策略决策 | 输出四席收益，由实验配置决定是否下一局 |

同样的 `ActionType.CHI` 在 t1 表示声明，在 t2 表示选择具体吃法，由 observation 的决策阶段区分。数学 bot 可以在声明前通过公共的纯函数分析自己的所有潜在吃法；被选中进入 t2 后，仍按正式候选提交一次选择。

### ✅ 6.2 仅在 Bot 路径适配候选与执行之间的差异

- **吃法不受 UI 数量限制。** 当前 `build_chi_option()` 超过五种会折叠为 manual，真人继续使用此合同。`bots/common_bot_helper/decision.py` 从本席可见手牌枚举完整候选，调用已有 `is_valid_chi_selection()`、`build_chi_detail_payload()` 校验规则及生成副露语义；driver 按当前 t2 模式提交 listed 选项或具体手选牌。优先复用已有规则函数，不为了 bot 修改真人的候选格式、数量阈值或选择流程。
- **t3 的 PASS 是提示确认。** 当前选项生成器始终附加 PASS，但执行器只允许在有未过的胡/杠提示时提交，且 PASS 后仍须出牌。bot 候选不暴露这种无独立策略价值的步骤。仅当目标座位由 bot 控制且其选择 DISCARD 时，driver 才在同一串行执行过程内先按需过提示，再按绑定 ID 出牌；记录完整引擎动作。真人仍自己确认提示或按原规则超时处理。
- **同值出牌去重。** 仅 bot 默认每种牌值一个候选，执行层绑定确定的自家实体牌。若有同值摸牌，优先绑定该摸牌实体，以保留“摸到即打”的可观察语义；否则按固定规则选择。特定托管控制器可以要求精确打出 `drawn_tile_id`。排序、视觉分组不扩充 bot 策略动作空间；真人指定的实体牌和分组不经过这一步去重或重排。
- **吃法按真正的规则效果去重。** 以消耗牌多重集和结果副露语义为依据；确认展示差异不影响规则/计番后才能合并，不能按随意的列表顺序生成重复动作。
- **杠选项完整展开。** 每个可暗杠牌值、每个可加杠副露分别成为候选。
- **HU 暂不选择胡法。** 当前引擎通过规则适配器选最高番，bot 只决定是否胡；如以后允许选胡法，另行扩展规则和动作版本。

适配层对 DISCARD 的提示确认只是 bot 命令展开，不修改引擎优先级或过牌规则。执行前校验决策及 bot 控制权仍有效，并在房间/会话的串行通道提交。不能在计算结束后用旧候选操作新的窗口或已归还真人的座位。

`ActionOption.priority` 用于响应裁决，不是策略价值；bot 不能将“杠优先于碰”解释成“应该优先选择杠”。

## ✅ 7. 无 UI 的 Arena 与基础评测

### ✅ 7.1 最小运行接口

```python
request = env.reset(seed=42)
while not request.terminal:
    bot = bots[request.player_id]
    action = bot.act(request.observation, request.legal_actions)
    request = env.step(request.decision_id, action.action_id)

returns = request.returns  # 四席本局 score_delta
```

这是建议的串行多玩家接口：每次给运行器一个决策请求，`step()` 后自动推进确定性流程，直到下一个真实决策或终局。终局结果使用单独类型；示例仅展示快速模式的控制关系，`bot.act()` 的实际执行也应由有预算的运行器包装。

有限时模式由 `ArenaRunner` 负责并发派发、接收结果以及按时调用 `env.tick(now)`；状态修改仍串行。不能在唯一的调度线程里同步等待 `act()` 返回后才检查时间。所有提交都以运行器当前单调时钟重新检查期限，不能拿请求创建时的旧时间提交来绕过超时。

t1/t4 的策略按隐藏提交处理。环境可以顺序调用各席策略，但后调用者看不到先调用者的意向；调换调用顺序不能改变同一组意向的裁决结果。向单席策略暴露其他待行动者名单也可能泄露资格，不直接透传运行器内部调度信息。

Arena 的**快速模式**使用 `TimeoutConfig()` 关闭牌局操作计时，不等待 UI 当前约一秒的出牌延迟；bot 计算预算仍生效。**有限时模式**使用真实单调时钟及配置的 t1～t4，等待与超时行为遵循引擎。实时人机混打继承该局开局计时设置，保留真实 t1 等待和所有已确认的计时规则。禁止把快速模式的配置带入真人会话，也不因某席换成 bot 就重置计时。

增加最大决策数/自动推进步数保护。触发保护应报告轨迹和运行错误，不能悄悄记成正常流局。算法非法动作在开发/训练中直接失败；交互模式可按明确规则降级，并记录故障率。耗时较长的搜索/推理不能占住房间锁；需要硬超时隔离时用可终止的工作进程，不能只超时等待却留下无限计算任务。

### ✅ 7.2 两种期限与限时执行

**牌局操作时限**由引擎当前窗口决定，是 t1/t2/t3/t4 的实际截止时间。**bot 计算预算**是运行层对一次决策允许投入的时间，两者分开配置。

首版默认 bot 每次最多计算 **500 ms**，可按实验/席位配置；这是运行器执行的预算上限，系统调度和引擎提交另有可测量的开销，不是毫秒级硬实时承诺。提前算完立即返回，不人为等待凑足预算；关闭牌局计时也不取消计算上限。神经网络、数学分析和搜索遵循相同上限。

运行器采用如下截止规则：

```text
D_compute = min(T_request + B_compute, D_game - safety_margin)
```

`T_request` 从运行层接受该待处理决策时起算，`B_compute` 是计算预算；没有牌局期限时将 `D_game` 视为无穷大。预留提交、校验与调度余量 `safety_margin`，初值建议 50 ms，可配置并通过真实计时测试调整。已有时间不足时直接进入保底处理，不再启动昂贵任务。

排队、观察/候选构造、进程通信和推理等开销都消耗该请求的剩余时间；不能等进入 `act()` 才重新给满额预算。重复派发或失败重试也不刷新期限。模型在独立准备阶段加载/预热，并有启动超时；未就绪时使用保底控制器，不能在房间锁内加载模型。

数学/搜索 bot 定期检查剩余预算，在截止前返回当前最佳合法候选。运行器同时监督工作进程；超出预算仍不返回的任务停止接收结果并终止/隔离，回收过程不阻塞牌局调度。普通 `Future.result(timeout=...)` 或设置一个协作取消标记，不能单独解决死循环仍占用 CPU 的问题。使用预启动、数量有上限的工作进程，禁止超时后不断增开进程或累积任务。

当前实现中，超时/异常进程退出后该席本局继续使用保底，下一局再准备进程；不会在局中反复重启故障策略。非法返回在默认严格模式下直接报开发错误。

### ✅ 7.3 预算用尽、牌局超时与默认动作

运行器先准备廉价的保底动作，再运行耗时策略；完整吃法枚举或评分失败也有退路。保底策略固定版本并计入评测，所有动作仍须通过原引擎校验。

| 情况 | 处理 |
| --- | --- |
| bot 计算预算到，牌局期限尚未到 | 作废该次耗时任务，立即为该 bot 提交预设保底动作，不额外等到 5 秒或 30 秒 |
| t1/t4 的 bot 保底 | 提交 PASS；t1 已开启计时仍等待完整窗口，t4 按原引擎规则可在全部响应后提前裁决 |
| t2 的 bot 保底 | 放弃本次吃法选择，沿用现有 PASS 入口 |
| t3 的 bot 保底 | 按需过本席胡/杠提示；本次摸牌实体仍在则打它，否则按固定的现有视觉顺序选择合法出牌 |
| 当前牌局期限已到（`now >= D_game`） | 先调用 `expire_timers(now)`，使用引擎原有的 t1/t2/t3/t4 超时结果；不提交迟到策略或另行覆盖引擎动作 |
| 请求已失效或控制权已变化 | 丢弃策略及保底结果，不操作新窗口或真人座位 |

“预算到后的主动保底”和“引擎操作超时”是两个不同事件。例如 t3 真正超时仍按引擎的视觉最右规则出牌，不把真人或引擎超时规则改成摸切。若保底提交时已错过牌局期限，同样改由引擎超时处理。

对一次决策最多接受一个最终结果；保底已经执行后，迟到的最佳动作不能再生效。自然进入 t2、杠后补牌等新决策可以得到新的计算预算，但游戏时限只按引擎规则更新；t4 返回 t3 时不得另给完整 t3 操作时长。

### ✅ 7.4 同时响应与测试时钟

t1/t4 中，各 bot 的请求按同一窗口调度并尽早派发，隐藏各家的响应内容。它们共享该窗口的实际期限，不能按座位顺序分别阻塞等待 500 ms，导致后面的 bot 等前面的 bot 算完才开始计时。若工作进程暂不可用，排队也计入预算，到期即保底。

有限时 t1 即使所有人提前响应，也按引擎规则等待完整窗口；等待的是牌局规则，并非 bot 在持续计算。其间继续推进调度和其他合法操作，不忙等，也不占住房间锁。

计时逻辑可注入测试时钟，用事件推进验证期限前、恰好到期和过期后的行为，避免测试真的等待每个 5/30 秒。确定性测试固定任务完成/超时事件；实机有限时评测另外使用真实单调时钟，记录机器、进程并发、耗时与超时。不能用虚拟时间跳过推理后宣称通过了真实计算时限，也不承诺同种子在不同负载下得到相同限时策略轨迹。

### ✅ 7.5 三个基线

1. `TsumogiriBot`：不主动吃碰杠胡，摸到即打；无本次摸牌时按确定规则出牌。作为流程和最低基线，不自动等同于当前 UI 的“打最右张”。
2. `RandomBot`：从去重后的候选均匀随机选择，用于覆盖流程。
3. `WinThenRandomBot`：有合法 HU 则胡，其余随机，作为比完全随机更有解释性的弱基线。

断线托管规则另有用途，继续遵循 [联机设计](multiplayer_design.md) 中已确认的定义，不因引入策略 bot 而替换。

### ✅ 7.6 收益和基础指标

主目标先定为**每局期望筹码变化**，直接取 `RoundResult.score_deltas`。流局收益为零；一炮多响、点胡、自摸、抢杠都使用引擎的实际付款结果。

不把最高番、胡牌率、听牌率或“是否第一名”替代主目标。需要打整场排名时再明确局数与终局效用。训练可使用固定正比例的收益缩放；裁剪收益或加入中间奖励会改变学习目标，必须单独记录并做对照。

辅助报告：胡牌率、放铳率、流局率、番数/赔付分布、决策耗时分位数、每秒局数、非法动作率、计算预算超时率、牌局超时率和保底使用率。耗时分别记录端到端延迟、排队和策略计算时间，归因清楚区分策略失分与运行器降级。

评测采用固定种子集、四席轮换、固定对手池和一致计算预算，同时报告平均收益及置信区间。轮换版本属于相关样本，应按牌山种子分组统计，不能当成完全独立对局。训练种子、调参种子、最终测试种子分开；发牌种子只由运行器持有。

先用约 100 个种子做流程冒烟，再按实测方差扩充评测规模。不以少量连胜或“胜率高一点”宣称进步。后续对手池包括旧版本快照，避免只对一种弱对手有效。

### ✅ 7.7 可复现记录

记录代码版本及工作区改动标识、规则/配置/观察/动作/特征版本、牌山与各席 RNG 种子、bot 参数或模型摘要、候选顺序、选中动作和四席结果。另记运行模式、每席计算预算、安全余量、保底版本、各截止/完成事件及结果是否迟到。UUID 与真实计时不作为逐字一致的复现目标；跨机器严格对照策略时另用固定采样次数/工作量预算，并与实机时限达标测试分开报告。

自对弈数据记录每次真实决策前的 observation、完整候选、选中候选、行为概率（适用时）、阶段及终局收益。中间自动动作保留审计轨迹，但不伪装成 bot 决策。

训练过程可另存服务器私有真值用于复现、监督标签或集中式 critic，但这份数据与策略输入分开。不得把“复盘时知道所有手牌”当成策略决策时的可见信息。

## ✅ 8. 数学 bot：P2 基线与 P3 距离/概率分析

### ✅ 8.1 第一个可用版本

首版已实现以下策略：

1. ✅ 有合法 HU 时直接接受，作为基线约定。❌ 胡与继续打的完整期望收益比较尚未实现。
2. ✅ 枚举出牌后的手牌，在预算内检查合法听牌、不同胡牌方式的付款和未见张数；分析结束与中断明确区分。
3. ✅ 按有效待牌/付款代理值和覆盖多胡型的组形启发式排序。❌ 基于对手行为校准的放铳风险尚未实现。
4. ✅ 吃碰比较副露后的手牌和后续出牌；杠按未见牌等可能模型平均补摸后的组形/即时自摸价值，并施加固定保守罚项。❌ 杠后的完整听牌价值与抢杠风险后验尚未实现。

✅ `bots/math_bot_helper/analysis.py` 已提供 `ReadyAnalyzer`，组合现有 `RuleAdapter.evaluate_win()`，输出不可变纯数据，区分点胡/自摸的起胡条件和基础赔付。内置规则用合法组模板与现有传统/特殊胡型检查器筛掉不成立的形状，再调用原计番；不扩展现有 `RuleAdapter` 的必选方法，也不替换真人 UI 的规则入口。

✅ `ReadyAnalysis.is_ready` 为三态：找到合法待牌时 True；完整分析且无合法待牌时 False；中断且尚未找到待牌时 None。`complete`、`checked_tiles`、`errors` 和各候选状态用于说明分析范围。零未见张数的理论待牌保留，但不进入有效待牌评分。

✅ `MathBot.last_decision` 和 Arena 私有轨迹包含逐候选 `ActionScore`；预算中断不会被记作“没有听牌”。吃牌声明最多精细分析组形最好的八个“吃法＋后续出牌”方案，截断标记保留在说明中。副露后的组形与杠的补摸平均仍是启发式，不能称为完整 EV。

特别约定测试加牌的位置：`evaluate_win()` 的点胡/抢杠路径会自行加入胡牌牌张，自摸路径要求该牌已在手牌中。新听牌适配不能把两种路径都追加一次而多算一张。

### ✅ 8.2 未见牌统计

对每种牌值建立计数：

```text
U(t) = 规则总张数(t) - 自己暗手张数(t) - 已知公开实体牌张数(t)
```

公开统计包含自己的副露。当前弃牌、被领取后进入副露的牌、正在公开声明的加杠牌等，按实体流转只计一次；不能同时累加全部弃牌历史与全部副露。

`U(t)` 包含对手暗手和牌山中的未知牌，不等于牌山里实际还有几张。在不考虑对手行为信息、未知牌等可能分配的基线模型下，可以用 `U(t) / sum(U)` 估计下一次未知抽取的牌值分布；必须标明这个假设。利用对手历史后，需要新的信念模型。

听牌价值可以先用“未见待牌数量 × 对应付款”的启发式，但它不等于完整期望收益：还缺谁会先胡、点胡出现率、放铳风险和剩余摸牌次数。

### ✅ 8.3 距离、动态规划与概率（首版）

✅ `bots/search_bot_helper/distance.py` 定义库存约束的补牌距离，提供分支剪枝、七小对动态规划、精确进张和完成状态。P2 的部分搭子支持仍保留为廉价排序特征；它允许乐观重叠，不作为精确距离。`math` 的策略行为保持原版，`search` 使用新的分析。

**牌型补牌距离**：对给定固定副露的胡牌形状目标暗手多重集 `W`，在 `W[t] <= H[t] + U[t]` 下求 `sum(max(0, W[t] - H[t]))` 的最小值。它描述缺几张目标牌，不直接表示真实对局还需几次摸牌；同一张牌不能同时用于两个组。距离只检查形状，不包含起胡门槛，`D=0` 不能替代合法胡牌候选或规则计番结果。

覆盖算术胡、无副露的传统胡、七小对（包含连七对）和清龙；特殊胡型仍按当前计算器的“暗手＋固定副露”总牌检查，杠后总牌数不为 14 时不启用这些特殊目标。`complete=True` 时给出确切值或证明库存内不可达；中断时 `value=None` 并保留 `lower/upper`，不把已找到的上界伪装成最优解。完整结果的缓存包含算法版本、手牌、固定副露及未见数量。

后续逐步加入：

- ✅ 逐牌值计算能降低距离的进张；`Ukeire` 保留检查范围和完成状态。❌ 自适应多步改良路径的精确概率尚未实现。
- ✅ 目标牌数不超出公开未见库存，完整搜索可证明形状不可达。❌ 包含起胡门槛和赔付的全目标优化尚未实现。
- ✅ 固定自摸待牌集合的有限次无放回命中概率（超几何计算）；它忽略竞争胡牌和期间换听，❌ 不是实际先胡概率。
- ✅ 未知牌无放回分配到假想对手暗手和牌山，进行截断模拟。
- ✅ P3.5 已有基于公开库存、副露与阶段的危险/喂牌指标和攻守取舍。❌ 校准后的放铳概率、损失和行为后验尚未实现。

缓存按规则、手牌计数、副露语义及胡牌上下文建立；依赖可见数量的结果把相应计数纳入 key。不要用完整私有 GameState 作策略缓存 key，以免无意让隐藏信息影响输出。

## ✅ 9. 搜索：从自己的信念采样（实验版本）

`bots/search_bot.py` 提供独立 `SearchBot`，不替换 `MathBot`。首版只搜索 t3 出牌：先保留 P2 的合法选择和评分，在最多三个候选上进行距离/进张分析，再执行成批 Monte Carlo rollout。胡牌、吃碰杠、响应和吃法选择继续委托 P2。流程如下：

1. `bots/search_bot_helper/belief.py` 用当前可见数量、各席暗手张数和剩余牌山长度检查守恒，将未知实体均匀随机分配；待加杠的已知牌保留在来源暗手里。历史传给后续观察，但暂不用于行为后验。
2. 各根动作使用同一个假想世界；只有整批候选都完成才记录样本，预算中断的半批全部丢弃。
3. `bots/search_bot_helper/rollout.py` 在独立 `GameState` 中使用现有规则执行。各席后续策略优先胡、否则摸切/过，只接收各自投影观察和候选，不能读取假想牌山或对手暗手。
4. 默认至多四个世界、每次 16 个引擎转移左右；同时响应会完成当前响应批。终局使用有界筹码收益，未终局使用有界组形潜力，且真实胜负的值超出截断叶子的取值区间。它是待评测的截断启发式，不称为完整筹码 EV。
5. 保存逐候选距离界、进张完成状态、P2 原评分、最终评分、样本均值/方差和整批计数；未搜索候选没有最终搜索分。只有比较的所有根完成精确距离/进张时才应用对应修正，部分结果仍保留为诊断。

策略拿不到真实服务器的私有快照来搜索。假想世界必须从自己的可见信息重建；rollout 中各席策略也只能看到对应席位的观察。

均匀分配未知牌是第一版近似，不是经过行为推断的后验。朴素 determinization 还可能让不同隐藏世界中的后续策略分别利用本不该知道的信息，形成过于乐观的结果；作为实验基线评测，不宣称已经解决不完全信息搜索。

✅ 当前从 observation 构造局部 t3 假想状态，未读取真实局快照。❌ 尚未支持所有阶段的搜索重建、强 rollout 策略、行为后验、完整终局收益估计或高吞吐内存 `fork()`。这些应逐项验证，不能用当前离线实验代替实时混打验收。

## ✅ 10. 神经网络：学习已有接口里的策略

推荐先做**状态与候选动作联合评分**：

```text
h = encode(observation, style_profile)
logit_i = score(h, encode(legal_actions[i]))
policy = softmax(logits over valid candidates)
value = critic(visible_state, style_profile)  # PPO 训练侧的风格终局效用；不进对局
```

这天然支持变长候选：出牌、不同杠和多种吃法共用候选评分，不必一开始构造巨大的固定动作编号。批处理时对 padding 做 mask，并保存候选语义顺序。

第一版输入：24 种牌值的自家计数、公开牌计数、各席副露与弃牌、相对座位、剩余牌山、分数、决策阶段、候选语义、风格参数及可选数学特征。先用小型 MLP 或简单集合编码器；是否增加循环网络/Transformer 由历史信息增益和吞吐量实验决定。筹码 value 可以是辅助预测，不能单独决定所有风格的策略目标。

训练优先级：

1. 用 P3.5 各风格产生带标签的模仿数据，验证模型能合法出招、复现教师的目标/攻守偏好并加速推理；保留目标和分析完成状态。
2. ✅ 已加入 PPO 自对弈实验（[PPO记录](../test_docs/bot_development_log.md#ppo)），检查风格保持并与原模仿版独立对照；❌ 更大规模强度提升和真人可玩性仍待验证。单独最大化终局筹码可能使风格趋同，因此当前使用明确的风格效用、参考分布约束、旧策略池与固定局面。

数据按局/种子划分，不能把同一局相邻决策随机拆到训练和测试两边。记录阶段、行为概率及旧模型版本，避免将搜索教师数据与在线策略数据混用却不处理分布差异。

强化学习要处理每席决策间隔不同的事实。先使用每局有限时域、终局结算与不折扣收益，避免按人工调度步数折扣而改变游戏目标。只有明确需要时才引入中间价值/奖励。

## ✅ 11. CFR/MCCFR 基础实现与后续验收

✅ 已新增独立 outcome-sampling MCCFR、Kuhn 已知小博弈、完整麻将观察适配、平均策略 `CfrBot`、检查点和独立训练/评测入口；精确版完成 5,337 局用户训练与 128 局冻结对照，确认表命中为 0%。✅ 后续另加固定分类器与五种合法规则的共享抽象版本，320 局学习后新局命中约 18.7%，详见[抽象 CFR记录](../test_docs/bot_development_log.md#cfr-abstract)。❌ 尚无收益或风格改善证据，长时间 Kuhn 收敛、全面限时场景与在线适应仍待完成。实现见 [CFR 设计](cfr_design.md)，原版瓶颈见 [一小时 CFR 记录](../test_docs/cfr_1h_evaluation.md)，新入口见 [抽象 CFR](../training/CFR_ABSTRACT.md)。下述理论边界继续适用。

需要区分三个目标：离线自对弈学策略、对当前局面做实时求解、根据真实对手持续适应。它们可以共享基础环境，但不是同一种训练循环。

CFR 在信息集上更新反事实遗憾，并通常输出平均策略；不是“某个动作输了就降低权重”。MCCFR 通过特定采样和权重估计遗憾，outcome sampling 还可用于在线遗憾最小化。参见 [CFR 原论文](https://papers.nips.cc/paper/3306-regret-minimization-in-games-with-incomplete-information.pdf) 与 [MCCFR 原论文](https://www.cs.cmu.edu/~waugh/publications/nips09b.pdf)。

本游戏虽然筹码收支平衡，但仍是四人不完全信息博弈，不能直接套用两人零和游戏的纳什收敛结论。多人方法可以通过实验得到强策略；这与具有同样的理论保证是两回事，可参考 [Pluribus 原论文](https://doi.org/10.1126/science.aay2400)。

推理阶段仍可使用 `act(obs, legal)`，训练阶段需另有接口：

- 与可观测历史对应的信息集 key；同一信息集内候选语义一致，不包含完整牌山、对手暗手或 UUID。
- 受训练器管理的分支复制、合法动作转移、终局四维收益。
- 机会节点/随机发牌与摸牌机制的概率合同；采样方案对应的到达概率和重要性权重。
- 对自身策略、对手策略及平均策略的存储与采样；不能把普通 rollout 均值当成反事实价值。
- 同时响应的隐藏承诺建模：可顺序展开，但后行动者的信息集不能包含先行动者的未公开意向。

真实模拟局可以预先洗完整牌山；CFR 训练适配仍须说明它是在采样初始机会结果，还是逐次展开随机摸牌，不能在概率计算中把两者重复计算。

建议先在独立的小型已知博弈或明确版本化的缩小规则环境验证遗憾更新、采样估计与平均策略，再尝试完整算术麻将。不要为缩小实验悄悄改变正式牌池。完整四人版以实测收益和对手池表现为验收，不以自报“已收敛”为验收。

只想适应当前对手时，先尝试公开行为统计、对手策略模型和小规模在线参数更新；是否需要完整 CFR，由这些实验的效果决定。

- ❌ **慢 bot：** 人为让 `act()` 长时间运行或失败，验证此时真人依法可用的整理和响应请求仍能处理，后台计时仍推进；不能只测一个瞬间返回的随机 bot。
- ❌ **迟到结果：** 在实时入口覆盖超时、终局、换局、暂停/恢复，以及在同一窗口把 bot 控制权交回真人；旧结果全部作废，不能替真人点击过或出牌。离线已有对应失效请求测试，尚不等于实时联调完成。
- ❌ **隔离与依赖：** 接入后验证纯真人桌不自动启用 bot，客户端不接收 bot 执行映射/私有真值；缺少神经网络依赖也能运行原真人入口。
- ❌ **实际操作：** 既运行后端回归，也在真实浏览器中完成单人试牌、真人路径和新策略人机混打检查；Arena 测试通过不能替代该项。

现有测试可复用 `test_action_options.py`、`test_ui_hand_commands.py`、`test_hand_grouping.py`、`test_tile_selection.py`、`test_response_window_timing.py`、`multiplayer/test/test_bot_play.py`、`multiplayer/test/test_live_rooms.py` 和 `multiplayer/test/test_web.py`。新混打模式另加场景，不把原固定对手/纯真人模式的测试期望直接改成新策略行为。
