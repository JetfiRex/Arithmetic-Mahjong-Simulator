# 血战模式设计文档

本文档定义算术麻将血战模式的牌局继续、胡牌结算、一炮多响、庄家轮换和下一局流程。血战模式复用现有 t1、t2、t3、判胡和计番能力，但胡牌后不一定立即结束整局。

## 当前实现状态

- ✅ `GameMode.NORMAL` / `BLOOD_BATTLE` 与不可变配置，普通模式仍为默认值。
- ✅ 胡牌即时结算并退出，后续摸打、响应和自摸付款跳过已胡玩家。
- ✅ `BloodBattleScoringAdapter`、逐次 `SettlementEvent` 和最终 `RoundResult`。
- ✅ 一炮多响开关；同时赢家按座位距离排序，分别向点炮者结算，再从最远赢家之后继续。
- ✅ 第三家胡牌或牌山摸空结束，保留此前分数，手动下一局固定轮庄并重置退出状态。
- ✅ 复用现有 t1～t4；抢杠结算后继续，不改变普通模式的操作与计时。
- ✅ 真人房间及人机试玩共用每局模式选择、本局配置锁定、已胡只读状态和即时结算记录。
- ✅ 私有快照 v2 保存血战进度，并兼容恢复 v1 普通模式快照。
- ❌ 血战专用 Bot 观察、收益分析、训练和强度评测暂不开展；现有策略可按合法候选行动，不代表针对血战优化。

验证记录见 [血战实现验收](../test_docs/blood_battle_validation.md)。

## 模式配置

已实现稳定配置：

```text
GameMode:
  NORMAL
  BLOOD_BATTLE

GameConfig:
  mode: GameMode
  allow_multiple_hu: bool
```

`allow_multiple_hu` 决定同一张弃牌被多人声明胡牌时，是全部生效还是只选一位赢家。该配置在一局开始后不可修改。

引擎入口示例：

```python
from simulator import GameConfig, GameMode, GameState

game = GameState.new_game(config=GameConfig(mode=GameMode.BLOOD_BATTLE))
```

真人房间和人机试玩都在房主设置中选择“血战”，模式、计时和一炮多响仅在当前局进行时锁定。结算后房主点“下一局”进入安排阶段，可修改这些配置；确认开局才应用到新局，不改写上局结算或累计分数。普通模式同样支持多响开关。未传 `mode` 时沿用房间当前模式，新房间默认为普通模式。

## 庄家与下一局

庄家就是每局的起始玩家，两者没有区别。

每局结束后，无论发生以下哪种情况，下一局庄家都固定轮换到当前庄家的下家：

- 流局。
- 庄家获胜。
- 闲家获胜。
- 血战完成三家胡牌。

```text
next_dealer_seat = (dealer_seat + 1) % 4
```

结算完成后停留在 `ROUND_ENDED`，不自动开始下一局。UI 先展示胡法、番数、赔付和最终分数，玩家手动点击“开始下一局”后才提交：

```text
start_next_round()
```

开始下一局时：

- 保留四位玩家的累计分数。
- 更新庄家和起始玩家。
- 创建新的 `round_id`。
- 清空上一局手牌、副露、弃牌、赢家和临时 Action 状态。
- 重建并洗牌牌山，重新发牌。

## 血战玩家状态

`PlayerState` 已增加：

```text
is_out: bool
win_order: int | None
win_settlement_id: str | None
```

玩家胡牌并完成即时结算后：

- 标记为 `is_winner = true` 和 `is_out = true`。
- 记录第几位胡牌以及对应结算事件。
- 手牌和副露冻结，不再变化。
- 不再摸牌、出牌、吃、碰、杠、胡或提交 `PASS`。
- 不再出现在后续 t1 响应者和后续自摸付款人中。
- 已公开的弃牌、副露和结算信息继续保留。

后续牌局只在尚未胡牌的玩家之间进行。

吃牌的“下家”同样跳过已退出玩家。退出玩家仍可查看牌桌和结算，其个人掉线不再暂停尚未结束的血战；房主离线关房的既有规则不变。

## 座位距离

从某个座位沿下家方向计算距离：

```text
seat_distance(source, candidate) = (candidate - source) % 4
```

- 距离 `1` 是下家。
- 距离 `2` 是对家。
- 距离 `3` 是上家。
- 距离 `0` 是本人，不作为其他玩家响应距离。

所有“最近赢家”“最远赢家”和“下一位玩家”都使用这个方向，并跳过已经 `is_out` 的玩家。

## 一炮多响关闭

别人弃牌后，t1 仍允许所有有胡牌选项的玩家提交 `HU`，避免提交时间影响结果。t1 结束后：

1. 收集全部合法胡牌声明。
2. 如果只有一位，直接确定该玩家获胜。
3. 如果有多位，只保留距离点炮者最近的一位。
4. 其他胡牌声明不生效，声明者继续留在牌局中。
5. 完成赢家的即时结算并将其移出牌局。
6. 如果本局尚未结束，从赢家的下家开始寻找下一位未胡玩家。
7. 该玩家先摸一张牌，再进入新的 t3。

## 一炮多响开启

同一张弃牌上的全部合法胡牌声明同时生效：

1. 按它们距离点炮者的下家方向距离从近到远排列赢家。
2. 每位赢家分别生成最高番胡法和即时结算结果。
3. 点炮者分别向每位赢家付款。
4. 所有赢家同时标记为 `is_out`。
5. 如果累计已有三位玩家胡牌，立即结束本局。
6. 否则以本次距离点炮者最远的赢家为锚点，从其下家开始寻找下一位未胡玩家。
7. 该玩家摸一张牌后进入新的 t3。

示例：

```text
座位顺序: 1 -> 2 -> 3 -> 4 -> 1
1 点炮，2 和 3 同时胡：
  2、3 同时完成结算并退出。
  本次最远赢家是 3。
  下一位未胡玩家是 4，因此 4 先摸牌。
```

```text
1 点炮，2、3、4 同时胡：
  三家同时完成结算。
  已有三位赢家，本局立即结束，不再安排下一位摸牌。
```

## 自摸后的继续流程

玩家在自己的 t3 选择自摸胡后：

1. 不再打牌，因此不创建 t1 或 t2。
2. 调用规则黑箱确定最高番胡法。
3. 立即完成本次自摸结算。
4. 胡牌玩家退出后续牌局。
5. 如果累计已有三位赢家，结束本局。
6. 否则从胡牌玩家的下家开始寻找下一位未胡玩家。
7. 下一位玩家先摸一张，再进入 t3。

点胡只有一个生效赢家时，也使用同一条“赢家下家中的下一位未胡玩家摸牌”规则。

## 即时结算规则

血战模式每次胡牌立即结算，不等到第三家胡牌后统一计算。

### 自摸

自摸发生时，所有尚未胡牌且不是本次赢家的玩家分别向赢家付款。

示例：

```text
玩家 1 首先自摸：玩家 2、3、4 分别付款给 1。
之后玩家 2 自摸：玩家 1 已退出，只由玩家 3、4 分别付款给 2。
```

当只剩两位未胡玩家时，自摸只有一位付款人。

### 点炮

点炮只由点炮者向赢家付款。开启一炮多响时，点炮者分别向每位同时获胜的玩家付款。

当只剩两位未胡玩家时，无论自摸还是点炮，都只有另一位玩家付款，因此付款人数相同；结算记录仍必须保留真实胡牌方式。

### 已胡玩家

已经 `is_out` 的玩家：

- 不参与后续付款。
- 不参与后续收款，除非处理的是其已经确定的本次胡牌结算。
- 已经获得或支付的分数不会因为后续流局而回滚。

## 结算数据

一次胡牌生成一个 `SettlementEvent`：

```text
settlement_id
winner_id
win_order
win_method
source_player_id
winning_tile
winning_groups
fan_items
total_fan
capped_fan
base_payment
score_deltas
```

一炮多响为每位赢家分别生成一个 `SettlementEvent`，但它们可以共享同一个弃牌事件 ID。

实际合同沿用 `win_result` 包含胡牌方式、胡法、番种和基础赔付，`score_deltas` 记录实际付款；新增 `win_order`，不改变原有字段的含义。

整局结束后生成 `RoundResult`：

```text
round_id
mode
end_reason
dealer_seat
next_dealer_seat
winners_in_order
remaining_player_ids
settlement_events
final_scores
final_player_states
event_log
```

`winner_ids` 保留以兼容旧调用者，`winners_in_order` 是公开序列化中的同值别名。`final_player_states` 只包含座位、分数和退出/胡牌状态；`event_log` 是公开事件摘要，不包含摸牌值、私有手牌和未裁决意向，也不是完整回放播放器。已胡玩家的胡法可从对应结算事件查看，完整牌山仍只在整局结束后提供。最终结算页直接提供“查看牌山”，安排下一局期间也能回看上一局，确认新开局后关闭；本人先胡、其他人尚在继续时不公开牌山。

## 流局

### 普通模式

牌山摸空且无人胡牌时结束本局，四位玩家本局分数变化全部为 `0`。

### 血战模式

牌山摸空但尚未出现三位赢家时也结束本局：

- 不产生新的流局赔付。
- 流局这个事件本身给所有玩家增加的分数变化为 `0`；尚未胡牌者此前支付的分数仍计入整局净变化。
- 此前每次胡牌已经产生的即时结算继续有效，不回滚。
- `RoundResult` 汇总此前全部 `SettlementEvent`。

## Phase 流程

点胡：

```text
WAITING_RESPONSE
-> RESOLVING_ACTION
-> SETTLING
-> ROUND_ENDED（已有三位赢家）
   或 WAITING_DRAW（下一位未胡玩家）
```

自摸：

```text
WAITING_TURN_ACTION
-> SETTLING
-> ROUND_ENDED（已有三位赢家）
   或 WAITING_DRAW（下一位未胡玩家）
```

`SETTLING` 不接受玩家动作，也不使用 t1、t2 或 t3。它负责调用规则和结算适配层、更新分数、冻结赢家并生成结算事件。

## RuleAdapter 与 ScoringAdapter

`RuleAdapter` 负责：

- 判断是否可胡。
- 在所有合法胡法中选择最高番结果。
- 返回展示所需的牌组、番种和番数。
- 隔离以后对胡牌要求、番种表和封顶规则的修改。

`ScoringAdapter` 负责：

- 根据普通/血战模式确定付款人。
- 根据自摸、点炮或抢杠生成每位玩家的分数变化。
- 处理一炮多响的多份结算。
- 保证所有 `score_deltas` 总和为 `0`。

GameState 不根据番种名称写分支，只消费两个 Adapter 的稳定返回值。
