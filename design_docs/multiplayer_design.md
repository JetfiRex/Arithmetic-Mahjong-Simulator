## 1. 第一版做成什么

第一屏提供“创建房间”和“加入房间”，体验参照用户描述的 TTS 房间，而不是注册登录或自动匹配。

以下为完整已确认要求；当前本地版实际完成范围以第 0 节为准，不能将整条正式联网要求视为全部完成：

1. 创建房间时填写房间名、密码和自己的用户名；创建者成为房主。
2. 加入时填写正确的房间名、密码和自己的用户名，不做注册登录系统。
3. 每房最多 10 人，包含房主、打牌者和观战者；每局恰好四人打，不足四人不能开始。
4. 房主每局指定哪四人打；房主可以自己观战、不参加打牌。未开局可调整，开局后本局参赛人员和座位锁定。具体座位建议由房主安排，见第 4 节。
5. 由房主确认开局，不额外要求“四位玩家全部点击准备”。上一版的强制四人准备流程被本次要求替代。
6. 其他成员可选择上帝视角或不看任何人手牌的公共视角观战。上帝视角可看四家手牌和操作倒计时，不看牌山顺序或未裁决的操作意向。
7. 房主可以踢人；对正在打牌者被踢后的接管方式，见待确认项。
8. 全服限制每个人同一时间只能加入或创建一个房间。原先按 IP 硬限制会影响共用网络及换 IP 重连，替代识别方案仍待确认，不能直接以相同 IP 自动认领旧身份。
9. 房主个人掉线直接销毁房间，不保留、不转让，也不等待 300 秒；服务器/运行后端的电脑故障则影响所有房间，并要求设计保存和恢复原对局。管理员关闭网页不影响游戏。
10. 非房主的打牌者掉线后暂停全桌，保留原操作剩余时间，等待本人 300 秒；未回来则由默认 bot 接管该席，本局后续原则为“摸什么打什么”。重连显示名可能变化，不用用户名作为恢复身份的依据。
11. 每局结束后，房主可重新指定参赛人员；离席者座位上的分数不清零，下一位坐上去的人继承该座位分数。
12. 对局正常结算之后，允许复盘查看该局牌山顺序；进行中的牌山顺序不能通过上帝视角或复盘接口泄露。

庄家仍按原规则每局固定轮换，胡牌、流局、番数和付款规则不因换人或联网而改变。

本次不扩展血战、策略 AI、注册账号、匹配、排行榜、聊天或付费。断线默认托管属于必要的流程控制器，不是策略 AI。结算后查看牌山顺序纳入范围，但完整逐步回放播放器仍可后做。

后续独立扩展已接入普通/血战模式选择与血战即时结算，详见 [血战设计](blood_battle_design.md)；策略 Bot 使用独立的人机试玩入口。以上范围描述保留本阶段的原始目标。

验收仍从本机隔离会话、局域网设备推进到外网；采用何种 IP/身份限制后按该明确策略测试，不能为方便测试而在正式环境偷偷放宽。

## 3. 总体架构与技术选择

推荐继续使用 Python 后端和现有原生 HTML/CSS/JS，不为联网重写成另一套游戏。

```text
每房最多十个浏览器成员，其中四个参赛，其余观战
  HTTP：创建/密码入房、房主选人/踢人/开局、提交动作、重同步
  WebSocket：接收属于本人的最新状态、连接状态及通知
             |
      联机服务：身份验证 + 房间管理
             |
      每个房间独立的运行层
      串行处理动作、超时/断线/托管、按成员角色生成视图
             |
      现有 GameState
             |
      现有 RuleAdapter / ScoringAdapter
```

建议的网络层为 **FastAPI + Uvicorn**，浏览器使用原生 WebSocket；动作仍走 HTTP JSON，保留现有 `fetch` 的交互习惯。WebSocket 主要负责服务器主动推送，不强求所有动作都改为 WebSocket 消息。FastAPI 官方提供 WebSocket、依赖注入和断线处理支持。[官方文档](https://fastapi.tiangolo.com/advanced/websockets/)

第一版每次推送“按成员和观战权限过滤的完整当前视图”，不做复杂增量补丁或事件重放。先保证恢复简单、结果一致，再根据测量优化。

当前采用单进程、单 worker，每个房间在内存中运行，关服清空；引擎私有快照能力保留，但不接入当前服务。单进程不等于只能容纳一个房间；每个房间必须有独立状态，但不承诺未经测试的容量。内存中的连接和房间不能靠直接增加 worker 来共享，FastAPI 官方也明确说明了示例内存连接管理的单进程限制。[官方说明](https://fastapi.tiangolo.com/advanced/websockets/#handling-disconnections-and-multiple-clients)

仍不急着引入 Redis、微服务或多进程。现在明确先设计并实现保存/恢复能力，不再沿用“内存丢了重新开一局”的默认方案；恢复规则详见第 7 节及 [保存与恢复设计](state_recovery_design.md)。

## 4. 房间、身份与开局

### 房间与牌局不是同一个状态机

本地已实现下列正常房间阶段及重启暂停叠加态；个人断线和正式网络故障分类仍为后续设计，不替代引擎 `GamePhase`：

```text
WAITING_PLAYERS -> PLAYING -> REVIEWING -> ARRANGING -> PLAYING
PLAYING -> SUSPENDED_PLAYER_GRACE -> PLAYING
服务器故障恢复 -> SUSPENDED_SERVER_RECOVERY -> 等原房主/成员恢复
房主个人断线 -> CLOSED / ABORTED
任意允许关闭的状态 -> CLOSED
```

`GameState.phase` 继续负责摸牌、t1/t2/t3/t4、结算。不要把“等待朋友进房”塞进麻将回合阶段。

上述 `SUSPENDED_SERVER_RECOVERY` 是正式方案的概念名；当前本地实现使用独立 `recovery_pending` 标记，不新增或改写正常房间 phase。

`REVIEWING` 只在已有正常结算结果后进入；所有房间成员可自行点牌山查看，房主也没有提前查看特权。房主提交带原 `round_id` 的 `prepare_next_round` 后进入 `ARRANGING`，全房停止查看，才能改座位。此时引擎仍保持上一局 `ROUND_ENDED`，不轮庄、不洗牌、不改分。保存座位不等于开局；最终 `start` 校验四席及房间版本后才调用 `start_next_round()`。不能直接从 `REVIEWING` 通过 `start`/`assign` 跳过房主结束查看步骤。

房间至少保存 `room_id`、房间名、密码哈希、房主成员 ID、最多十个成员、四个座位及累计分数、下一局安排、本局参赛映射、观战模式、连接与断线状态、配置，以及自己的 `GameState` 和运行上下文。

### 创建与密码入房

- 创建表单：房间名、房间密码、用户名；计时和一炮多响等对局设置在房主的开局面板中配置。
- 加入表单：房间名、房间密码、用户名；未通过密码校验不能读取成员列表、手牌或观战数据。
- 建议仍存活的房间名在全服唯一；名称规范化规则需要明确，避免空格或大小写造成两个看起来相同的房间。内部用随机 `room_id` 区分，旧房间关闭后同名新房不继承旧凭证。
- 建议用户名在同一房间内唯一，允许不同房间重名；这是显示和辨认规则，不是注册账号，也不能用同名方式抢回别人的身份。
- 密码只存加盐的专用密码哈希，不能存明文或可逆密文，不发给观战者或写入日志；推荐使用成熟的 Argon2id 实现，而不是自行设计哈希。[OWASP 密码存储指南](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)
- 错误密码、暴力试房名、创建房间和重复加入需要限速。原先“邀请链接凭证直接入房”的方案取消；后续若提供链接，只可预填房间名，不能绕过密码。

### 不注册账号，但必须有身份

- 第一次访问时，服务器创建匿名会话，使用不可猜测的随机凭证；用户名用于人类辨认，真正的权限由服务器签发的凭证识别。用户不需要看到登录页面。
- 正式环境用 `HttpOnly`、`Secure`、适当 `SameSite` 的 Cookie 绑定会话；不把席位凭证写进邀请链接或普通日志。
- 房间密码只证明可以申请入房，不代表能操纵任何已占用的座位；房主身份和成员身份分别由服务器授权。
- 服务器按会话确定 `player_id`，绝不相信请求体中的 `player_id`、`seat` 或 `is_host`。
- 重连时用户名可能改变。建议原浏览器保留随机会话/恢复凭证，以此恢复同一 `member_id` 和原席位，再更新显示名；不能凭新名字、同 IP 或房间密码认领别人的手牌。清除浏览器数据或跨设备恢复，可考虑额外恢复码，待确认。
- 同一个浏览器会话开多个标签页，仍是同一个成员，不占两个名额；不能靠改用户名变成第二个人。
- 同一玩家允许多个标签页查看；所有写操作仍按同一身份校验及去重，不会增加席位。断线状态按该玩家是否还有有效连接判断。

IP 只用于限制，不替代成员凭证。相同 IP、用户名或密码都不能作为恢复原玩家的充分证明。

### 全服单房间限制与 IP 的替代方案

- 已确认范围为全服：每人同时只能加入或创建一个房间，房主、参赛者、观众都占这一资格。掉线保留原房间时不能换个用户名再另开房间，仍可恢复原房间。
- 不能把这一限制误写成“一 IP 只能发一个请求或建立一条连接”。同一成员的 HTTP、WS、刷新和多标签页不能互相把对方当成第二人踢掉。
- 同一路由器/Wi-Fi 下的多人，可能在服务器看来共用一个公网 IP；严格限制会让他们无法一起进入。NAT 可以将多个内部地址映射到同一个外部地址，这不是简单检查能区分的。[RFC 3022](https://www.rfc-editor.org/rfc/rfc3022)
- VPN、动态 IP 和 IPv6 地址变化也意味着 IP 不能可靠等同于一个自然人；这条规则是入场限制，不承诺彻底杜绝多开或串通。
- 只信任已配置的反向代理提供的来源地址，不能任由请求伪造 `X-Forwarded-For` 绕过限制，也不能把代理自己的地址误当成所有玩家的 IP。[MDN 安全说明](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/X-Forwarded-For#security_and_privacy_concerns)
- **建议、待确认：用服务器签发的匿名凭证绑定唯一身份，维护全服 `identity -> active_room`；IP 只用于限流与异常检测，不再硬性一 IP 一人。** 同一 Wi-Fi 下的不同凭证可正常进入；同一凭证换 IP 仍恢复原席，而不是创建新成员。该建议放宽了原 IP 硬限制，须确认后才实现。
- 同一凭证短线重连不新占名额；旧连接与新连接要交接写权限，旧请求不能在新连接恢复后继续出牌。主动离房、被踢或房间销毁后按相应规则释放全服单房间占位。
- 成员的房间归属、断线保留与资格释放要持久化并原子更新，不能服务一重启就允许同一身份同时控制两个房间。容量、角色和单房间限制都必须校验，而不是只在页面隐藏按钮。
- 不注册账号的方案只能约束同一个匿名身份，无法证明一个自然人没有使用无痕窗口、清除 Cookie 或换设备另建身份。IP 硬封也无法可靠解决这一点；不以侵入式浏览器指纹冒充真实身份认证。若需要更强防多开，另议管理员发放的入场码，而非宣称当前能绝对保证每个自然人一个身份。

### 房主选人与踢人

- 房主从房间成员中把四个不同的人安排到 seat 0/1/2/3；未被指定的人观战。房主不强制占 seat 0，也不强制参赛。
- 未开局时可以换人和调换座位；开局条件为四个席位都有不同且在线、仍有入房权限的成员，由房主最终确认。第一版不额外加入强制准备按钮。
- 首局庄家默认 seat 0，以后沿用现有固定轮庄规则。
- 开局时保存不可变的本局参赛名单与座位绑定；普通成员不能抢座，房主也不能在本局中把另一人塞进已经锁定的座位。
- 建议允许对局中途入房的新成员只观战，仍受 10 人、密码和 IP 限制；房主到下一局才可安排其参赛。
- 房主可以踢观众、待开局成员或正在打牌的成员；踢掉正在打牌的人不能顺便改变本局参赛名单。建议该席立即交给默认托管，本局不换真人；这个接管时机需要确认。
- 踢人须撤销其本房间读写权限和现有连接；旧凭证、旧 WS 和晚到命令不能继续操作。能否重新输密码进房、是否需要房主解除禁止，列为待确认。
- 房主不向别人转移身份，也不能通过“踢自己”触发隐式转让。上一版“房主退出自动移交房主”的提议取消；掉线按用户要求联动整房处理。
- 每局结算后进入安排面板，房主可以保留原四人，也可从观众中换人，并修改普通/血战模式、一炮多响和计时，再确认下一局。配置仅在本局内锁定，确认开局才生效。

房主权限是管理房间，不是代替四席出牌、改分、改牌山或默认窥视私牌。房主如果本局观战，可以和其他观众一样选观战视角。

### 成员与计分座位分离

- `member_id` 表示进入房间的这个人；`seat_id` 表示四个长期存在的计分位置，两者不能混用。
- 四个座位从建房开始有自己的累计分数，初始为 0。观众没有独立参赛分数，房主也不因是房主而有额外分数。
- 本局换人锁定；下一局 A 离开 seat 2、B 坐上 seat 2 时，B 从 seat 2 的现有分数继续，不是从 0 开始，也不把 A 的分数带去其他座位。
- 同一个成员下一局换到另一个座位，继承新座位的分数，不带走旧座位的分数。空座期间分数也保留，不足四人时禁止开局。
- `GameState` 内 p0/p1/p2/p3 可继续代表绝对座位，但网络身份必须先经本局映射才能操作对应 p 值，不能把 p0 当成固定房主或永久的某个成员。
- 每局结算保存当时的参赛成员和名字、座位、分数变化，避免下一局换人改名后，把上一局赢家误显示成新来的玩家。
- 换人本身不触发结算、不产生分数变化，也不改变庄家固定轮换规则。只有创建新房间才初始化一套新的座位分数。

## 5. 私有视图与开发者模式隔离

### 按成员角色分别生成快照

联机快照包含 `viewer_member_id`、本局角色、观战模式，以及参赛时的 `viewer_player_id` / `viewer_seat`。观众的参赛席位为空，不把观众伪装成 p0，也不因是房主就返回某席私有操作。

可以公开：座位、昵称、在线状态、庄家、当前行动席、手牌张数、已公开副露、各家弃牌、牌山剩余张数、已完成结算。

参赛者只收到自己这席的手牌牌值和实体 ID、手牌顺序与分组、当前可选操作、本人已提交意向、本人吃法候选、本人倒计时及暂停剩余时间。

默认不发给其他人：进行中的牌山顺序、未公开手牌、别人的合法操作列表、未裁决的响应类型、自动过名单和别人整理手牌的具体内容。上帝观战按本次确认额外开放手牌及操作倒计时，不把所有服务器私有字段全部放开。

| 角色/视角 | 手牌可见范围 | 操作权限 | 倒计时/未裁决意向 |
| --- | --- | --- | --- |
| 四个打牌者 | 只有本人的私牌 | 只操作本人的席位 | 只有本人有权看到的内容 |
| 公共观战 | 四家均只看手牌张数/牌背 | 无游戏操作 | 不提供其他人的私有计时或意向 |
| 上帝观战 | 可以看四家的手牌牌值 | 无游戏操作 | 可看当前适用的操作倒计时及暂停剩余时间；仍不可看未裁决意向 |
| 房主 | 按自己的本局角色判断 | 额外有选人/踢人/开局等房间权限 | 房主身份本身不增加可见范围 |

上帝视角已确认边界为“四家手牌牌值 + 倒计时”，不额外提供手牌实体 ID、私有分组、未裁决选项、进行中的牌山顺序、随机种子或修改能力。普通参赛者仍只看自己的倒计时，公共观众仍不看各席操作倒计时；上帝视角是明确的只读例外。不能直接调用 `reveal_hands=True` 就当作安全的观战视图。

建议观众可在公共/上帝视角之间切换，并向全房显示当前观战模式；本局参赛者即使掉线或托管，也不能在同一局切成上帝视角后再接回自己的牌。下一局重新发牌前，房主可正常把原上帝观众安排上场。

上帝观战者可以通过其他聊天工具透露手牌，系统无法阻止这种线下串通。这是用户主动允许的观看权限，不能同时承诺观战绝不带来作弊风险。

有人胡后，公开结算所需的赢家最高番胡法、番种和付款结果，保留此前确认的展示规则。正常结算之后允许只读查看该局完整牌山顺序，详见 [保存与恢复设计](state_recovery_design.md) 的复盘记录部分；这不自动意味着公开所有输家的完整私有分组。

牌序按独立 `round_id` 保留为服务器内存私有记录，当前服务不落盘，关服清空。当前已结算局在 `REVIEWING` 和 `ARRANGING` 都开放查询，最终结算页直接提供“查看牌山”；房主确认新开局后关闭旧局查询，没有跨局历史浏览/下载入口。不能因为房间曾经结算过，就放开新局牌山。血战必须整局结束才开放，已经胡牌但其余玩家仍在继续时不可查看。房主断线导致的未完成 `ABORTED` 局不冒充正常结算，是否开放另行确认。

### 过滤不只发生在手牌字段

网络层必须对白名单字段生成视图，并审查 `event_log`、`resolved_actions`、`payload`、错误响应和重连快照。不能把调试快照原样广播，再指望前端不显示敏感字段。

未裁决的 t1/t4 意向仅本人可见；其他人也不显示谁已点击、谁还没点击。日志不透传带私有事件空洞的原始序号，避免从序号变化推断隐藏事件。吃法数量和 t2 具体选择也只对执行者可见。

### 当前入口不暴露开发者能力

- 旧开发者入口和控制器已移除，仅保留供当前房间复用的牌桌资源。
- 新联机服务只注册正式房间与游戏接口，不注册编辑牌堆、编辑手牌、预置场景或调试重置接口。
- “隐藏开发者按钮”不等于隔离；即使手工构造 HTTP 请求，也不能调用这些能力。
- 联机测试用的确定牌山与场景注入通过进程内 fixture 完成，不增加可被外部访问的后门。

## 6. 同步、并发与请求合同

### 一份权威状态

洗牌、摸牌、合法性判定、响应裁决、计时和分数都以服务器为准。客户端只提交操作意图，不上传一份“算好的新 GameState”。

每个房间的玩家动作和超时推进进入同一条串行执行路径；不同房间互不修改状态。生成快照也读取一致状态，不在修改到一半时序列化。

规则计算是同步代码，接入异步网络框架时不能长时间阻塞整个网络事件循环。初版可在受控执行器中执行房间操作，仍保持同房间串行；同一房间的 timer tick 不能绕过它并发改状态。后台任务不得通过无限排队消耗内存。多房间计算延迟需要实测，不承诺线程能解决所有 CPU 容量问题。

### 不再用一个严格全局 revision 拦住所有动作

例如 A 正在 t3 出牌，B 同时拖牌；或者 t1 中 B 先点过，C 再点胡。B 的操作不应只因改变全局版本号，就让 A/C 的合法请求失败。

建议区分：

| 标识 | 作用 |
| --- | --- |
| `room_revision` | 房间成员、四席安排、权限和配置的版本 |
| `game_revision` | 公共游戏流程的版本；不因别人私有排序而递增 |
| `hand_revision` | 当前玩家自己的手牌内容、顺序、分组版本 |
| `view_seq` | 当前查看者的视图顺序，防止旧 HTTP 响应覆盖较新的推送 |
| `round_id` | 防止上一局的请求作用于下一局 |
| 当前窗口 ID | 防止旧 t1/t2/t3/t4 操作作用于新窗口 |

`view_seq` 在同一房间实例、同一查看者下递增，重连不重置；只因该查看者可见的内容变化而递增。服务器时间样本可独立更新，不要求每一秒产生状态版本。不同房间不能仅凭一个数字比较新旧。

校验以动作语义为准：出牌和整理要求自己的手牌版本与 t3 窗口匹配；t1/t4 响应校验对应窗口、本人资格和是否已提交，不因另一位玩家先响应就失效。`game_revision` 可用于定位状态，不要求所有命令与它严格相等。联机入口须强制传入所需窗口字段，不能因为底层参数可选就省略。

### 动作与确认

命令至少包含：协议版本、`command_id`、`room_id`、适用时的 `round_id`、命令类型、适用的窗口 ID，以及 `tile_id` / `option_id` / `group_id` 等 payload。涉及手牌的命令额外带本人的 `hand_revision`。房主安排席位的命令带 `room_revision`，开局时再次校验在线状态和四人绑定。

每个游戏命令还须校验本局 `member_id -> seat_id` 绑定、读写授权和是否已被踢/托管。网络重连的旧连接须失去写权限，恢复或换局不能让延迟请求作用到新任座位控制者。观众没有出牌、分组、吃碰杠胡过权限，上帝视角也不例外。

服务端从会话补全玩家身份，执行顺序为：鉴权、校验房间归属、检查重复命令、按服务器当前时间处理到期窗口、校验并执行动作、生成结果与新视图。

- 同一会话在同一房间内重试同一个 `command_id`，返回原执行结果，不再次出牌、扣分或开始下一局。
- 相同 ID 携带不同内容应拒绝；去重记录至少覆盖当前局，下一局请求还受原 `round_id` 限制。
- 当前状态应独立获取，不能把缓存的旧快照当作最新快照；客户端用 `view_seq` 处理 HTTP 与推送到达顺序。
- 错误码区分身份失效、无权限、窗口已过期、手牌版本冲突和非法动作。错误中不得附上未经本人过滤的状态或内部异常堆栈。
- 未确认的出牌/吃碰杠胡不在前端先永久生效；超时不等于服务器没执行，重试需沿用原 `command_id`。
- 排序可以显示本地拖动预览，但确认失败时以服务器视图恢复。第一版每次拖放才提交，不发送每一帧鼠标移动。

### 最小接口范围

| 接口 | 职责 |
| --- | --- |
| `POST /api/session` | 建立匿名会话 |
| `POST /api/rooms` | 提交房间名、密码、用户名，创建房间并成为房主 |
| `POST /api/rooms/join` | 提交房间名、密码、用户名，校验 IP/容量后返回成员身份 |
| `GET /api/rooms/{room_id}/state` | 鉴权后获取本人完整视图，供首次加载及重同步 |
| `POST /api/rooms/{room_id}/commands` | 提交安排座位、踢人、观战模式、开局、游戏动作、下一局等受校验命令 |
| `WS /api/rooms/{room_id}/stream` | 鉴权后推送本人视图、心跳和必要通知 |

HTTP 与 WebSocket 使用同一套身份和房间授权。广播指“向最多十名成员按其身份和视角分别发送状态”，不是发送同一个含全量私牌的 JSON。个人失联/服务器恢复暂停时只允许恢复相关操作；已因房主个人掉线销毁的房间不可继续读写或恢复。

慢客户端不能阻塞整个房间：使用有界发送队列，过慢时合并待发的完整状态或断开并要求重同步。动作执行结果与命令去重记录不随状态合并而丢失。

## 7. 计时与断线规则

### 沿用已确认的四种计时

- t1 默认 5 秒：所有座位每次出牌后都必须等满；全员提前过或只有过都不能提前跳过。启用时只有过的玩家不显示操作。
- t1 关闭：每位需要响应的真人都必须手动点击，包括只有过的人；最后一人提交后才裁决。
- t2 默认 5 秒：只用于吃；不超过 5 种列选项，超过 5 种手选恰好 3 张；无效、未完成或超时按当前已实现的 PASS 规则。
- t3 默认 30 秒：正常暗杠补牌后刷新；默认超时弃牌保持“散牌最右，否则最右分组最右”的规则。
- t4 默认 5 秒：只有合法抢杠者收到可操作的胡/过；普通参赛者只收到本人有权看到的倒计时，上帝观众可只读看倒计时，但不能替人选择。加杠者不能行动。全部过后完成加杠与补牌，恢复原 t3 剩余时间；有人胡则直接结算。
- 每种计时都可在每局开局前修改或关闭，本局内锁定；安排下一局时可重新设置，确认开局后应用。
- 拖动和分组仍只在任意玩家的 t3 允许；进入 t1/t2/t4 清理未确认高亮，保留已确认的顺序与分组。

房间正常运行时，后台任务独立推进 `expire_timers(now)` 和应当自动发生的摸牌；不依赖有人轮询、标签页处于前台或客户端发“超时”消息。联机房不再用三家固定机器人代替真人，仅在失联宽限结束等明确情况下接入默认托管。

服务端使用单调时钟作裁决，并发送本人可见的 deadline 和同一时钟基准下的服务器时间样本。浏览器仅估算显示剩余时间，本地显示 0 不代表请求一定有效或已经执行。

第一版以服务器在房间串行路径中开始处理时的时间判定是否到期，不按客户端提供的点击时间回填，也不自动补偿网速。边界统一为 `now >= deadline` 已过期；这条规则必须测试并在实际慢网环境验收。

### 失联的影响范围

| 失联者 | 已确认的影响范围 | 恢复方案状态 |
| --- | --- | --- |
| 普通观众 | 仅该观众断线，不影响四席游戏 | 建议保留短期重连资格，不暂停牌局 |
| 非房主的打牌者 | 暂停全桌 300 秒等待重连，逾期托管该席 | 已确认；恢复原计时，不能用户名/IP 冒领 |
| 房主，包括正在观战的房主 | 直接销毁本房间，其他成员断线 | 已确认不保留、不转让，不适用个人 300 秒宽限 |
| 运行后端的电脑/服务器 | 所有房间的所有成员掉线 | 已确认需要保存/恢复方案；关闭管理员网页不影响游戏 |

房主只是房间管理者，不必把规则计算放在房主电脑上。中央服务器仍可统一执行规则，同时按已确认的房主个人掉线规则关闭房间；不需要为了模拟这种体验先实现点对点连接。

在线判断由服务端连接和心跳决定，不信任浏览器主动声称“我一直在线”。刷新页面的短暂连接交替和同一成员的多个标签页需要容错，不能一条旧连接关闭就把整房踢下线。心跳检测阈值是运行参数，300 秒是检测到失联之后的恢复宽限，二者不能混为一个参数。

### 非房主打牌者的 300 秒宽限

已确认：离线选手在 300 秒内可回来；未回来则本局后续托管。300 秒不是 t5，不替代 t1/t2/t3/t4，也不是观众的操作时间。

**已确认：宽限期间暂停全桌。** 保存当前 t1/t2/t3/t4 的剩余时间、已经提交的响应、吃牌细节和 t4 内嵌的暂停 t3，不重置窗口或重新发牌。所有选手暂时不能继续改变游戏或整理牌，观众只能读取冻结画面，房主仍可管理成员。

这 300 秒不消耗任何原游戏计时，不先触发原 t3 timeout。恢复或转托管之后才继续原剩余时间，不能默默把宽限当成不影响 deadline 的旁路倒计时。

- 宽限结束前恢复：凭原身份恢复本局原席，补发完整视图并恢复原剩余操作时间，不赠送完整 t1/t2/t3/t4。允许重新找房间，重连流程先尝试认回该凭证对应的原成员；显示名变化不创建新身份，也不清零等待时间。
- 宽限到期：该席转为默认托管，其他人继续打，本局不塞入新的真人替换。
- 多人失联时分别记录各自宽限，不因为第二人掉线就重置第一人的时间；只有所有必要等待解除或转托管后，才恢复冻结的牌局。
- 房间级的“等待某人重连，还剩多少秒”可以公开显示。各席操作倒计时继续按角色控制：参赛者只看自己，公共观众不看，上帝观众可看冻结后的剩余量。
- 反复掉线是否每次都给 300 秒，以及逾期回来能否解除托管，均见待确认项。

### 默认托管的精确定义

这是确定性默认操作，不判断牌型价值，不追求赢牌：

- t1：选择 PASS，不吃、不碰、不明杠、不胡。启用 t1 仍等满剩余时长，不因托管者都过就跳过；关闭 t1 时托管者可代替失联者提交 PASS，仍等待其他真人。
- t2：若接管时原本正在选吃法，按 PASS，不自行选择组合。
- t3：先过掉自摸/暗杠/加杠提示，不主动胡或杠；若本次摸入的实体牌还在手里，按它的 `drawn_tile_id` 打出，即使失联前把它拖进组里也不误打另一张同值牌。
- 若接管发生在没有新摸牌的 t3，例如刚碰/吃完，或本次摸牌已不在手中，则回退为“散牌最右，否则最右分组最右”。这与正常 t3 timeout 分开定义，不能简单调用最右弃牌冒充摸什么打什么。
- t4：若有抢杠资格选择 PASS，不主动抢杠；继续遵守全部过后的原 t3 恢复规则。
- t3 被关闭也必须自动出牌，否则托管仍会卡住；具体短延迟属于运行节奏，不改变玩家配置的计时规则。
- 托管命令与真人命令、timer tick 进入同一串行通道，并验证当前控制权。真人恢复控制与自动出牌不能各执行一次。

### 房主个人掉线直接销毁房间

已确认不保留房间，取消上一版的 `SUSPENDED_HOST` 和“等房主 300 秒恢复”提议；房主即使只在观战，也适用此规则。

1. 服务器确认属于房主个人失联，而非全服服务器故障后，将房间置为终止；未完成局标记 `ABORTED`，不伪装成正常胡牌或流局。
2. 撤销成员对该房间的读写权限、关闭所有房间连接，释放全服单房间占位；其他房间不受影响。
3. 原房间 ID 不能重连续局；房主回来可以重新建房，但不能借同名恢复已销毁房间。
4. 关闭/删除标记必须持久化，服务重启不能从旧备份把已销毁的房间重新救活。此前已完成的结算历史是否长期保留不等于保留可继续玩的房间。

“掉线”以经过连接交接和心跳容错后的失联判定为准，不是旧 WS 刚关闭就立即删房。刷新能否成功交接必须测试；不能通过无限延长容错变相实现用户已经否定的房主恢复宽限。

### 管理员/服务器掉线，以及服务重新启动（历史恢复方案）

以下保留原恢复需求；用户后来选择每次开服重置，旧存档适配现已移除，当前不承诺停服后恢复原房间。

已确认：“管理员掉线”指运行后端的电脑/服务器断网、进程退出、主机不可用等，不是管理员关闭管理网页，不另做管理员网页在线心跳来控制全服。

仅网络暂时不可达、服务进程仍在时，内存可能保留；服务进程崩溃/重启时，内存方案无法恢复。不能宣称“重新连上就能回原局”，却完全不保存状态。

**实施优先级已确认：先补保存/恢复，再做联网房间。** 建议全服恢复后保留原房间并先暂停，由各房原房主和成员重新接入。停服时间不算游戏超时或个人 300 秒，不一次性补跑离线期间的出牌；具体全服恢复等候期限仍待确认。

- 使用服务器私有的版本化完整快照，优先采用 Python 标准库 SQLite 存储；保存安全的会话恢复信息、房间/成员/四席与分数、本局名单、完整牌山与手牌、实体 ID、分组、副露、窗口、已提交响应、计时剩余量、结算与命令去重信息。
- 恢复文件必须有版本与规则版本校验，私牌仍只在服务器保存；不能用不可信 pickle 或暴露一个“上传任意服务器状态”的接口。
- 不能把原进程的单调时钟绝对 deadline 直接搬到新进程，应保存剩余量并在恢复时重建时间基准。恢复不重新洗牌、重复摸牌、重复扣分或改变分组 ID。
- 若承诺已确认动作重启不丢失，状态与去重/结算记录须原子提交后才向客户端确认，不能只定时存一份落后快照。

必须区分两类关闭原因：服务故障产生的恢复快照可以继续；已经确认的房主个人掉线/主动关房不能复活。服务启动时所有旧连接必然不存在，不能立刻把所有原房主判定为个人掉线而销毁恢复数据。

如果后端进程还活着、但服务器的网络整体出了故障，单凭某条 WS 关闭或所有心跳同时消失，未必能准确判断是全服网络还是客户个人问题。需要服务器健康/网络故障信号、全服恢复保护态及保守分类；原因不明时先保护快照、暂停，不立即批量删房。具体判断阈值及恢复等候策略列入待确认项，不承诺网络错误能被绝对准确自动归因。

核心存档和 SQLite 能力保留，旧开发者与本地房间重启恢复适配已移除；当前 `multiplayer.web` 每次重启清空，不加载旧记录。个人连接交接、宽限与默认托管也已在新入口实现；疑似全服同时断链先保护，但准确网络故障归因和真实隧道验收仍未完成。详见 [开服设计](hosting_design.md) 与 [保存与恢复设计](state_recovery_design.md)。

## 10. 到时需要准备什么

现在先不需要买服务器或域名，也不需要改家庭路由器。

本机与局域网阶段需要：运行中的 Python 环境、隔离的测试会话和设备；如需监听局域网地址和放行系统防火墙，实施时单独确认。`127.0.0.1` 只表示访问者自己的电脑，不能作为朋友的访问地址。

同一台机器的四个浏览器上下文通常仍共享来源 IP；如果通过同一公网出口访问，同一局域网的四台设备也可能被一 IP 一人挡住。当前本地原型不实施 IP 硬限制，明确用独立窗口身份测四席；正式环境的身份/IP 方案仍待确认，不能在公网接口接受客户端自报测试 IP 或偷偷增加测试放行。真实多人验收需要符合最终确认的 IP 策略。

外网阶段需要：能持续运行后端的服务器/托管环境、可访问的域名或平台分配地址、HTTPS 证书，以及服务维护方式。现有程序有 Python 权威状态和实时连接，不能只上传 HTML 到纯静态托管就完成联网。

不推荐把当前开发者端口直接映射到公网。当前使用的 `http.server` 官方明确不推荐用于生产环境；应先完成正式联机入口和权限隔离。[Python 3.13 官方文档](https://docs.python.org/3.13/library/http.server.html)

推荐同域名提供页面、API 和 WebSocket，减少跨域与会话配置。公网只开放必要入口，后端放在受控代理后；部署方式参考 [Uvicorn 官方部署文档](https://uvicorn.dev/deployment/)。不在这一版直接启用多个 worker。

HTTPS/WSS 不是唯一安全措施：握手和命令都需鉴权，校验允许的 Origin，HTTP 写请求增加 CSRF 防护，限制消息大小与频率，不记录 Cookie、房间密码、恢复凭证或完整私牌。相关边界参考 [OWASP WebSocket 安全指南](https://cheatsheetseries.owasp.org/cheatsheets/WebSocket_Security_Cheat_Sheet.html)。本机或受信局域网的明文测试例外必须显式配置，不能沿用到外网环境。

## 12. 下一轮建议先做什么

本轮按最新目标完成每次开服重置、ASGI 入口与个人断线流程，可先在 [8771](http://127.0.0.1:8771) 本机体验。旧测试服务已移除，当前还提供独立的 [8772 人机试玩](http://127.0.0.1:8772)。

下一项为用户这轮明确暂缓的计划第 3 项：准备 Cloudflare 后接 Access 验签与稳定身份绑定，确认丢凭证/跨设备策略，再先保护域名、后发布 Tunnel，最后做真实外网四席、认证到期及隧道中断验收。

本轮没有创建 Access/Tunnel、请求密钥、购买域名或修改防火墙；当前只监听本机，不能将“新网络入口已实现”理解为“已经可以安全公开给外网”。

已确认的产品需求与仍待确认的恢复建议分别保留，新增实现时只为真正完成的条目打勾，不把“已有单机基础”或“已写设计”当成“联机已完成”。
