# Action 和 Timeout 设计

本文档描述第三阶段牌局引擎中 action、响应窗口和四个 timeout 的设计，并记录后端实现进度。

## 设计目标

算术麻将比普通麻将更依赖玩家手动整理手牌和判断组合，因此 action 系统需要同时满足：

- ✅ 玩家可以在任意玩家的 t3 内拖动和分组自己的手牌。（Board State、旧窗口校验、单人试牌与四人开发者 UI 已实现）
- ✅ 出牌后，其他玩家有时间决定是否吃、碰、杠、胡或过。
- ✅ 只有吃牌可能进入二次选择；胡、碰和杠均不进入 t2。
- ✅ timeout 可配置；关闭 timeout 时，系统必须等待玩家手动确认。（t1、t2 吃牌、t3、t4 抢杠）
- ✅ UI 不能因为“只显示过按钮”而泄露某个玩家没有响应选择的信息。（后端可见选项已处理）

## 当前实现状态

- ✅ `RESPONSE_WINDOW / t1`：响应提交、等待/超时、动作优先级、一炮多响配置以及同级座位距离裁决均已实现。
- ✅ `DETAIL_SELECTION / t2（吃牌）`：不超过 5 种时展示全部吃法；超过 5 种时由玩家选择恰好 3 张牌；无效、未完成或超时均按 `PASS` 处理。
- ✅ 吃牌胜出后，会按照分组设计中的实体牌选择优先级移除对应牌。
- ✅ 胡牌不会进入 t2；判胡时规则计算器已经选择最高番胡法，玩家不手动选择。
- ✅ 普通点胡、自摸和流局的正式结算已实现；`round_result` 暴露最高番胡法、番种、番数、赔付和分数变化。（单人试牌 UI 已接入）
- ✅ 普通 t3 动作后端已接通：自摸、暗杠、加杠、出牌及显式 `PASS`。
- ✅ 只有加杠可被抢；有合法抢杠者时进入 t4，暂停 t3，禁止常规操作。
- ✅ 所有人过时完成加杠和补牌，恢复原 t3 剩余时间；有人胡时直接结算，不再恢复 t3。
- ✅ 倒计时仅对有权操作的玩家本人可见，其他玩家拿不到相应 deadline。

## 文件规划

建议新增：

```text
simulator/actions.py
```

用于存放 action 相关的数据结构。

后续如果 resolver 变复杂，再拆：

```text
simulator/action_resolver.py
```

第一版可以先把 resolver 逻辑留在 `GameState` 或一个小型 helper 中，等吃碰杠胡都接入后再拆。

## 核心概念

### ✅ ActionType

第一版 action 类型：

```text
PASS
DISCARD
CHI
PENG
MING_GANG
AN_GANG
JIA_GANG
HU
```

未来可以增加：

```text
DRAW
CANCEL
SELECT_DETAIL
```

`DRAW` 可以继续由 GameState 内部推进，不一定暴露为玩家 action。

### ✅ ActionRequest

玩家提交的动作意图。

建议字段：

```text
request_id
player_id
action_type
payload
submitted_at
source_window_id
```

`ActionRequest` 只是意图，不直接修改 GameState。系统收到后需要：

1. 验证当前 phase 是否允许。
2. 验证该玩家是否拥有这个 action option。
3. 保存请求或进入下一步裁决。

### ✅ ActionOption

系统提供给 UI 的可选动作。

建议字段：

```text
action_type
priority
payload_options
requires_detail
display_hint
```

例如别人打出一张 `3` 后，下家可能看到：

```text
CHI:
  payload_options:
    - required_values: [1, "+", 2]
      tiles: [1, "+", 2]
      preview: "1 + 2 = 3"
PASS
```

如果某玩家只有 `PASS`，是否显示取决于 `t1` 是否开启，详见下文。吃牌的 `payload_options` 可能很多，UI 不一定总是全部展示，详见 t2 的吃牌细节设计。

### ✅ ResolvedAction

系统裁决后的动作。

建议字段：

```text
action_type
player_id
source_player_id
claimed_tile
payload
reason
```

如果 `GameConfig.allow_multiple_hu = true`，`HU` 可以产生多个 resolved action 或一个包含多个 winner 的结果；关闭时只保留沿点炮者下家方向距离最近的赢家。

## ✅ Timeout 配置

开发者 UI 默认开启 `t1=5`、`t2=5`、`t3=30`、`t4=5` 秒。开局前可单独修改秒数（1 到 600 秒）、关闭某项或全局关闭计时；关闭映射为对应字段的 `None`。开局后配置只读，服务端拒绝修改，手动下一局沿用原配置。需要改动时必须显式结束当前游戏并返回开局设置。UI 控制器和运行层见 `UI/game_session.py`、`UI/server.py`，不改变引擎默认关闭计时的基础合同。

四人开发者局中的三个对手不吃碰杠胡，只自动过并按固定节奏打最右张；真人只看到自己的剩余时间。对手不会主动加杠，所以真人抢杠 t4 不会自然出现；真人加杠遇到有资格的对手时仍走真实 t4，并由对手立即过。不要为了展示倒计时伪造资格或向无资格者显示 t4。

GameState 建议持有一个 timeout 配置：

```text
TimeoutConfig
  discard_response_seconds: float | None
  action_detail_seconds: float | None
  turn_action_seconds: float | None
  rob_kong_seconds: float | None
```

对应：

- `t1 = discard_response_seconds`
- `t2 = action_detail_seconds`
- `t3 = turn_action_seconds`
- `t4 = rob_kong_seconds`

`None` 表示关闭该 timeout。

代码和文档中建议使用以下语义名称：

```text
t1: RESPONSE_WINDOW
t2: DETAIL_SELECTION
t3: TURN_DECISION
t4: ROB_KONG_RESPONSE
```

含义：

- `RESPONSE_WINDOW`：出牌后的公共响应窗口，决定是否有人要胡、杠、碰、吃或过。
- `DETAIL_SELECTION`：响应优先级确定后，胜出的吃牌玩家选择具体吃法或实体牌。
- `TURN_DECISION`：当前玩家摸牌后的本回合决策窗口，决定自摸、暗杠、加杠、打牌或过掉当前提示的可选动作。
- `ROB_KONG_RESPONSE`：加杠暂存后，仅允许具备抢杠胡资格的玩家提交胡或过。

### ✅ TimerState

当前正在运行的计时器可以表示为：

```text
TimerState
  kind
  started_at
  deadline_at
  timeout_seconds
```

`kind` 可选：

```text
RESPONSE_WINDOW
DETAIL_SELECTION
TURN_DECISION
ROB_KONG_RESPONSE
```

GameState 不需要自己 sleep。外部循环或前端轮询调用：

```text
expire_timers(now)
```

如果当前时间超过 deadline，GameState 根据当前 timer 的类型执行默认动作。

## ✅ Phase 设计（普通模式基础流程）

建议逐步演进为：

```text
INIT
DEALING
WAITING_DRAW
WAITING_TURN_ACTION
WAITING_RESPONSE
WAITING_ACTION_DETAIL
WAITING_ROB_KONG
RESOLVING_ACTION
SETTLING
ROUND_ENDED
```

### ✅ WAITING_TURN_ACTION

当前玩家摸牌后进入。

对应 `t3 / TURN_DECISION`。

可选动作：

- 自摸胡。
- 暗杠。
- 加杠。
- 打牌。
- 过掉当前提示的可选动作。

### ✅ WAITING_RESPONSE

某玩家打牌后进入。

对应 `t1 / RESPONSE_WINDOW`。

其他玩家可响应：

- 胡。
- 明杠。
- 碰。
- 吃。
- 过。

### ✅ WAITING_ACTION_DETAIL（吃牌）

响应优先级裁决后，只有胜出的动作为吃，并且需要玩家选择吃法或实体牌时，才进入此 phase。

对应 `t2 / DETAIL_SELECTION`。

胡、碰和明杠不进入此 phase。暗杠和加杠属于当前玩家的 t3 操作，也不使用 t2。

典型情况：

- 吃：选择哪几张手牌组成算式。

### ✅ SETTLING（普通模式后端）

胡牌裁决完成后进入。该 phase 不使用 t1、t2、t3 或 t4，也不接受玩家动作。

系统验证规则和结算适配层的返回结果，更新分数并生成公开的最高番胡法、番种明细、番数、赔付和分数变化。`SETTLING` 是同步内部阶段，完成后立即进入 `ROUND_ENDED`；UI 在 `ROUND_ENDED` 展示结果，直到玩家手动调用 `start_next_round()`。

流局也通过该 phase 生成不含赢家的结算结果。

### ✅ Phase 与手牌整理权限（Phase、旧窗口校验及单人试牌 UI 已实现）

手牌整理命令必须经过 Phase 验证：

| Phase | 拖动牌 | 创建/拆除分组 | 左键动作选牌 |
|---|---:|---:|---:|
| `WAITING_TURN_ACTION / t3` | 允许，四位玩家都可以整理自己的牌 | 允许，四位玩家都可以操作自己的分组 | 当前玩家可选择出牌、暗杠、加杠或自摸 |
| `WAITING_RESPONSE / t1` | 不允许 | 不允许 | 响应玩家选择吃、碰、明杠、胡或过 |
| `WAITING_ACTION_DETAIL / t2` | 不允许 | 不允许 | 胜出的吃牌玩家选择吃法或具体牌 |
| `WAITING_ROB_KONG / t4` | 不允许 | 不允许 | 仅有抢杠资格的玩家选择胡或过；加杠者不能行动 |
| 其他 Phase | 不允许 | 不允许 | 由对应流程决定 |

每次 t3 应具有自己的窗口身份。t3 结束时：

- 清空所有玩家尚未确认的右键待分组选择。
- 清空当前玩家尚未提交的左键出牌高亮。
- 不回滚已经完成的拖动、分组或拆组。
- 已确认的手牌顺序和 `HandGroup` 继续保留。

从 t3 进入 t1、t2 或 t4 时，原有待分组牌只取消高亮并恢复普通显示，不自动创建分组。暗杠或加杠补摸会启动新的 t3，旧 t3 的临时选择同样清空。

右键待分组选择和左键动作高亮属于 UI 临时状态，不写入 Board State。服务端只接收已经确认的移动、分组和 ActionRequest，并拒绝携带过期 t3/window id 的请求。

## t1：出牌后的响应时间

代码名：

```text
RESPONSE_WINDOW
```

触发时机：

```text
当前玩家打出一张牌 -> 创建 ResponseWindow -> 进入 WAITING_RESPONSE
```

进入 t1 时，所有玩家未确认的右键待分组选择都必须清空；t1 期间不能拖动、创建、拆除或修改分组。

ResponseWindow 建议字段：

```text
window_id
source_player_id
discard_record
opened_at
deadline_at
options_by_player
requests_by_player
auto_passed_players
status
```

### ✅ t1 开启时

当 `discard_response_seconds` 不是 `None`：

1. 系统为其他三家计算可选动作。
2. 如果某玩家只有 `PASS`，UI 不显示任何按钮。
3. 只有 `PASS` 的玩家被系统静默标记为 auto pass。
4. 有真实选择的玩家看到可选项。
5. 玩家超时未提交，则默认 `PASS`。
6. 必须等到本次 t1 的截止时间才统一裁决；即使所有需要响应的人已经提交，也不提前结束。

✅ 这是一段固定时长，不是“最多等待这么久”。四个座位的每一次出牌都遵循同一规则，真人出牌、下家出牌、对家出牌、上家出牌没有区别。三个自动对手都过、真人提前点过、玩家提前声明吃碰杠胡，都只记录响应，截止前不摸牌、不进入 t2、不执行副露，也不结算胡牌。t2 和后续 t3 从实际裁决完成时开始计时，而不是从点击按钮时开始。

关闭 t1 时仍在全部响应提交后立即裁决；本条不改变 t4 的“所有有资格者已决定即可提前结束”规则。

这样可以避免信息泄露：

如果 UI 给某个玩家显示“过”，而不给另一个玩家显示任何东西，旁观或联机场景下可能暴露“他没有可操作项”。t1 开启时，只显示真实选择，只有过的人静默空过。

如果其他三家都只有 `PASS`：

```text
不显示任何响应按钮。
仍然等待完整 t1。
t1 结束后系统统一空过，轮到下一家摸牌。
```

这条规则有意保留机械等待：如果系统看到三家都不能响应就立刻跳过，当前玩家会通过等待时长推断其他人的手牌没有吃碰杠胡机会。即使三家都只能过，也必须表现得像“有人可能正在思考”一样等待完整 t1。

### ✅ t1 关闭时

当 `discard_response_seconds` 是 `None`：

1. 不自动超时。
2. 所有其他三家都必须手动确认。
3. 即使某玩家只有 `PASS`，也必须显示并点击 `PASS`。
4. 所有人提交后才进入裁决或轮转。

这个模式更适合本地调试或无计时的慢速模式。

## ✅ t1 裁决规则（含一炮多响配置）

响应窗口结束后，按规则优先级裁决：

```text
HU > MING_GANG > PENG > CHI > PASS
```

细节：

- 胡牌候选始终优先于其他动作。
- `allow_multiple_hu = true` 时，全部合法胡牌候选同时成立。
- `allow_multiple_hu = false` 时，只保留离出牌者最近的合法胡牌候选。
- 如果有人胡，其他吃碰杠全部失效。
- 碰和明杠都高于吃。
- 多个碰或明杠同时成立时，离出牌者最近的玩家优先。
- 吃只能由出牌者的下家响应。
- 提交时间不决定优先级。

座位距离建议使用：

```text
distance = (candidate_seat - source_seat) % 4
```

距离越小，离出牌者越近。距离为 0 是出牌者本人，应排除。

## ✅ Action 裁决与分组选牌的衔接（t1、吃、碰、明杠）

本节描述的 t1 裁决以及吃、碰、明杠实体牌选择已经实现。暗杠和加杠不参与 t1 裁决，已通过下文的 t3 动作流程接入。

t1 动作优先级和实体牌选择应由两个独立步骤处理：

```text
ActionResolver:
  决定哪位玩家的 HU / MING_GANG / PENG / CHI 胜出

TileSelectionResolver:
  在动作与需求牌值确定后，决定具体消耗哪些 tile_id
```

推荐流程：

1. 当前玩家打牌，t3 结束；清空临时高亮并冻结所有手牌布局。
2. 进入 t1，根据各玩家完整手牌牌值生成可响应动作。
3. 收集 `HU / MING_GANG / PENG / CHI / PASS`，由 ActionResolver 按优先级和座位距离裁决。
4. `HU` 直接进入胡牌流程，不移除普通手牌。
5. `PENG / MING_GANG` 不进入 t2，立即调用 TileSelectionResolver，按分组优先级产生具体 `tile_id`。
6. `CHI` 进入 t2；玩家选定吃法或手动选择具体牌后，再调用 TileSelectionResolver。
7. 执行前再次验证这些 `tile_id` 仍在手牌中、分组版本未变化、动作仍合法。
8. 按 ID 移除手牌、清理空组并生成副露。

TileSelectionResolver 建议使用纯逻辑接口：

```text
select_tiles(
  player_hand_snapshot,
  required_values,
  selected_tile_ids=None,
  allow_explicit_selection=False,
) -> TileSelectionResult
```

返回值至少包含：

```text
tile_ids
selection_source: explicit | exact_group | containing_group | mixed
source_group_ids
```

t1 不需要提前决定具体实体牌。进入 t1 时布局已经冻结，因此等优先级裁决完成后再选牌不会出现分组在中途变化的问题。

## ✅ t2：吃牌动作细节选择时间

代码名：

```text
DETAIL_SELECTION
```

触发时机：

```text
t1 裁决出 CHI，并且需要选择吃法或实体牌 -> WAITING_ACTION_DETAIL
```

### ✅ 吃牌细节

吃牌必须先选择具体吃法。系统最终使用稳定 `tile_id`，不能依赖会随布局变化的数组下标。

payload 建议：

```text
required_values: [TileValue, TileValue, TileValue]
selected_tile_ids: [str, str, str] | None
claimed_tile: TileValue
```

系统验证：

- `selected_tile_ids` 存在时，玩家确实拥有这些实体牌。
- 这些手牌加上弃牌可以组成合法算式。
- 该玩家确实是出牌者下家。
- t2 期间手牌布局被冻结，因此验证失败后实体牌位置不会因为分组或拖动而变化。

### ✅ 吃牌选项展示策略

吃牌可能有很多种组合，全部展示会让 UI 变得很吵。建议使用阈值策略：

```text
CHI_OPTION_DISPLAY_LIMIT = 5
```

“可吃方式”按算式牌值方案去重。同值实体牌的不同 `tile_id` 不重复计算为不同吃法。

如果可吃方式数量不超过 5：

```text
UI 直接展示所有可吃组合。
玩家从列表中选择一种。
提交后系统再次验证。
```

玩家点击的是一个算式方案，例如 `[3, "+", 6] + 9`。选定方案后，系统再根据已确认分组执行实体牌自动选择优先级；不会因为手中有多张同值牌而显示多份相同公式。

如果可吃方式数量超过 5：

```text
UI 不展示完整组合列表。
UI 进入手动选牌模式。
玩家使用左键自行点击具体手牌并确认。
系统判断所选手牌 + 弃牌能否组成合法算式。
```

手动选牌模式下：

- 玩家应选择 3 张具体手牌，并提交稳定 `selected_tile_ids`。
- 只能选择恰好 3 张：少于 3 张或多于 3 张都不能吃，并默认 `PASS`。
- 如果所选 3 张加上弃牌能够组成合法算式，执行吃牌。
- 如果所选 3 张不能组成合法算式，默认 `PASS`。
- 玩家没有选择任何牌并确认，默认 `PASS`。
- t2 到期时仍未提交合法选择，默认 `PASS`。

上述无效提交会直接结束本次 t2，不允许在同一个 t2 内反复试错，也不会重新裁决低优先级响应。

这个策略既避免一次性展示几十种组合，也保留玩家自己整理算式的空间。

t2 的左键选牌是动作选择，不是右键待分组选择。进入 t2 前必须清空原有待分组高亮，且 t2 内不允许新建、拆除或修改分组。

吃牌 t2 超时：

```text
默认 PASS。
```

吃牌因无效选择、未选择、主动放弃或超时而 `PASS` 后，第一版不重新裁决低优先级候选动作，直接轮到弃牌者的下一家摸牌。

## 胡、碰和杠不进入 t2

### 胡牌

玩家在 t1 选择胡后，不再手动选择具体胡法。t1 裁决确认胡牌成立后，模拟器调用规则计算器黑箱，由计算器返回最高番的最终胡法。

如果存在多个同为最高番的胡法，也由规则计算器在黑箱内部确定一个稳定的最终结果。番种、番数和同分处理规则以后可以在计算器内部调整，不改变 Action 流程。

“不进入 t2”只表示玩家不需要在计时窗口内选择胡法，**不表示胡法对玩家隐藏**。确定最终胡法后，流程必须进入独立结算环节：

```text
t1 裁决 HU
-> 规则计算器选择最高番胡法
-> SETTLING
-> ROUND_ENDED（公开 round_result，UI 可展示胡法和结算明细）
-> 玩家手动开始下一局
```

结算时至少向 UI 暴露：

- 胡牌玩家；多人胡时为每位赢家分别提供结果。
- 胡牌方式，例如自摸、点胡或抢杠。
- 胡牌牌张以及最高番胡法对应的完整牌组/算式。
- 命中的番种明细 `fan_items`。
- 原始总番、封顶后番数和赔付结果。
- 每位玩家的分数变化。

Action 流程只负责把已经裁定的赢家和胡牌上下文交给结算层。详细计番、赔付和 `RoundResult` 数据结构继续由 `general_design.md` 中的 `ScoringAdapter` 与结束流程负责。

### ✅ 碰和明杠

碰不需要 t2，因为三张相同牌组成唯一动作，也不允许玩家手动选择具体同值实体牌。t1 裁决出碰后，系统直接根据分组自动选择优先级确定三张 `tile_id`。

明杠同样不需要 t2，也不允许玩家手动选择具体同值实体牌。t1 裁决出明杠后，系统根据同一套分组优先级确定四张 `tile_id`：

```text
selected_tile_ids: [str, str, str, str]
claimed_tile: TileValue
```

碰和明杠的自动实体选牌顺序为：完全匹配组、最左完整包含组、散牌优先再按组从左到右补齐。完整规则见 `hand_grouping_design.md`。

## ✅ t3：当前玩家行动时间（普通模式后端）

代码名：

```text
TURN_DECISION
```

触发时机：

```text
玩家摸牌 -> 新摸的牌追加到 hand_tiles 最右侧 -> WAITING_TURN_ACTION
```

对应玩家可以：

- 打任意位置的牌。
- 暗杠。
- 加杠。
- 自摸胡。
- 整理手牌顺序。
- 过掉当前提示的可选动作。

在任意玩家的 t3 内，四位玩家都可以拖动和分组自己的手牌。整理手牌顺序、创建分组和拆除分组不消耗 action，不改变 phase，也不重置 t3。当前玩家可以从普通分组或散牌区左键选择一张牌，再点击“出牌”按钮提交该实体牌的 `tile_id`。

t3 结束后，所有尚未确认的右键待分组高亮和左键动作高亮都要清空；已经完成的手牌拖动与分组变化保留。t1、t2 和 t4 期间冻结所有手牌整理操作。

UI 上只需要一个“过”按钮。代码层也建议继续使用 `PASS`，不要单独设计 `PASS_GANG`。`PASS` 的含义由当前 phase 和当前 action options 决定：

```text
RESPONSE_WINDOW 中的 PASS：放弃响应别人的弃牌。
TURN_DECISION 中的 PASS：暂时不执行当前提示的暗杠/加杠/自摸等可选动作。
DETAIL_SELECTION 中的 PASS：放弃当前胜出的细节动作，例如吃牌细节超时或主动取消。
```

如果当前玩家存在暗杠或加杠机会，UI 必须显示这些可选动作。玩家如果暂时不想杠，可以点击 `PASS` 后继续选择打牌。这样可以避免玩家误触打牌时跳过一个重要机会。

`TURN_DECISION` 中的 `PASS` 只表示放弃当前这次提示，不表示永久放弃这组暗杠或加杠机会。暗杠和加杠都不要求“立刻杠”：例如玩家摸到第 5 张 `3` 后可以暗杠，但也可以先不杠，之后自己的回合仍然可以选择暗杠，只要牌山还有可补摸的牌且手牌/明牌状态仍满足条件。

后端已经实现以下约束：

- 当前 t3 存在暗杠或加杠选项时，玩家必须先选择杠或提交 `PASS`，否则拒绝出牌。
- `PASS` 不结束 t3，也不刷新 t3 计时，只允许玩家继续整理和出牌。
- 当前 t3 提交 `PASS` 后，不再允许在同一个 t3 内执行已跳过的杠。
- 每次进入 t3 都生成新的 `turn_window_id`；杠后补牌会生成新窗口并清除旧 PASS 状态。
- 携带旧 `turn_window_id` 的 t3 Action 请求会被拒绝。

### ✅ 自摸胡牌

- 正常摸牌或杠后补牌创建的新 t3，可以出现自摸选项。
- 吃、碰后的未摸牌 t3 不生成自摸选项。
- 系统使用稳定的 `drawn_tile_id` 追踪本次摸到的牌；拖动或分组后仍以真正摸到的那张牌作为胡牌牌张。
- 玩家提交 `submit_turn_action(player_id, HU, now=..., source_turn_window_id=...)` 后，RuleAdapter 自动选择最高番胡法，ScoringAdapter 向另外三家各收一份赔付，生成结算并结束普通牌局。
- 胡牌不进入 t2，也不再要求打牌或开启弃牌响应窗口。
- `PASS` 可跳过本次胡牌和杠提示，不刷新 t3；该窗口内不再接受已跳过的自摸胡牌。
- t3 超时仍按默认弃牌处理，不自动胡牌。

### ✅ 新摸牌位置

新摸的牌默认追加到散牌区最右侧：

```text
player.add_hand_tile(drawn_tile)
```

玩家可以在 t3 内拖动这张牌到任意位置。

### ✅ t3 超时

当 `turn_action_seconds` 不是 `None` 且当前玩家超时：

```text
如果散牌区非空，默认打出散牌区最右侧一张牌。
如果所有手牌都已经分组，默认打出最右边分组的最右侧一张牌。
```

新摸的牌默认在散牌区最右侧，因此未拖动时通常会打出刚摸到的牌。玩家左键高亮了某张牌但没有点击“出牌”确认，也仍然执行上述默认规则。

如果超时时仍有暗杠或加杠机会未处理：

```text
默认视为 PASS，然后继续使用“散牌最右，否则最右组最右”的超时弃牌规则。
```

超时不会自动暗杠或加杠，因为这会改变牌局结构并暴露玩家选择意图。

### ✅ 暗杠和加杠选项（ActionOption）

暗杠和加杠可能同时有多个可选项。UI 应展示所有当前可执行的杠选项。

理论上同一时刻可选项数量很少，通常至多 2 种：

```text
AN_GANG: 某个手牌值有至少 5 张。
JIA_GANG: 已碰出的某个牌值，手牌中还有可加到该碰牌上的同值牌。
```

玩家可以选择其中一种杠，也可以点击 `PASS` 暂时不杠。未选择的杠机会不会永久消失，后续自己的 `TURN_DECISION` 中如果仍然满足条件，应再次显示。

### ✅ 暗杠和加杠补牌、时间刷新

如果玩家在 t3 内选择暗杠：

1. 执行暗杠。
2. 从牌山补摸一张。
3. 新摸牌追加到最右侧。
4. 重新开始 t3。

加杠同理：

1. 执行加杠。
2. 从牌山补摸一张。
3. 新摸牌追加到最右侧。
4. 重新开始 t3。

加杠先作为待定动作保存，不立即移除手牌或升级碰组。若无人有抢杠资格，直接完成加杠并补牌；若有人有资格，先进入下文 t4。有人抢杠胡时，不执行加杠也不补摸。

每次补牌都会重新生成暗杠、加杠、自摸和出牌选项，并创建新的 t3 窗口身份。暗杠和未进入 t4 的加杠仍重新启动完整 t3；进入过 t4 且最终所有人过的加杠，补牌后恢复暂停前的剩余时间。旧窗口中尚未确认的 UI 高亮应被清空。

### ✅ 牌山为空时禁止杠

暗杠和加杠都会要求玩家额外补摸一张牌。因此：

```text
如果牌山已经没有可摸牌，则不允许暗杠或加杠。
如果当前摸到的是牌山最后一张，摸完后牌山为空，也不允许暗杠或加杠。
```

UI 在这种情况下不应显示暗杠或加杠选项。GameState 也必须在提交动作时再次验证，防止前端状态过期。

### ✅ 吃碰杠的分组选牌优先级

因为同值牌具有不同 `tile_id`，吃、碰和杠必须明确移除哪些实体牌。统一优先级为：

```text
1. 玩家明确选择的实体牌（只适用于吃牌手动选牌）。
2. 最左边、内容与需求牌完全相同的分组。
3. 最左边、能够独自完整提供需求牌的分组；组内取最左匹配牌。
4. 先取散牌区最左匹配牌，再按组从左到右、组内从左到右补齐。
```

碰和明杠不适用第 1 级，直接从第 2 级开始：

```text
PENG: 完全匹配组是恰好包含所需 3 张同值牌的组。
MING_GANG: 完全匹配组是恰好包含所需 4 张同值牌的组。
```

如果一个组包含足够的同值牌但还有额外牌，则属于第 3 级：从最左边合格组中取最左边的所需牌，额外牌继续留在原组，分组不拆除。若没有任何单组能够完整提供，则按第 4 级跨散牌和多个组补齐。

暗杠复用上述完整优先级：玩家先在 t3 选择“杠哪个牌值”，然后系统依次尝试完全匹配组、最左完整包含组，最后才从散牌和多个组补齐。

加杠是明确例外。玩家先选择要升级的已有碰组，加入碰组的那一张同值牌直接跳过优先级 1、2、3，只执行优先级 4：

```text
最左边的同值散牌
-> 如果没有同值散牌，取最左边可提供该牌的分组中最左边的同值牌
```

暗杠和加杠具体需要的牌张数仍由合法动作结果提供，不由选牌器自行推断。

例子：

```text
别人打出 3，玩家可以碰。
若第一组恰好是 [3, 3, 3]，优先碰这一组。
若第一组是 [3, 3, 3, 8]，从该组取最左边三张 3，8 继续留在第一组。
若没有单组包含三张 3，则先取散牌中的 3，再从第一组、第二组依次补齐。
```

## ✅ t4：加杠的抢杠响应

代码名为 `ROB_KONG_RESPONSE`，timeout 字段为 `rob_kong_seconds`，默认 `None`。

### 触发与操作权限

1. ✅ 只在提交加杠时判断其他玩家能否以这张牌胡牌；暗杠、明杠不触发 t4。
2. ✅ 无人能抢时不创建窗口，直接按原规则完成加杠、补摸和刷新 t3。
3. ✅ 有人能抢时保存加杠方案及将使用的实体牌，不改碰组，不移牌，不补牌；暂停原 t3。
4. ✅ 只有能抢杠胡的玩家收到自己的 `HU / PASS` 选项和 t4 倒计时。不能抢的玩家和加杠者不收到 t4 提示数据。
5. ✅ t4 期间加杠者不能出牌、摸牌、继续杠或整理手牌；其他玩家也不能整理。仅合格响应者可以提交胡或过。
6. ✅ 每人只能提交一次最终响应；拒绝无资格玩家、重复请求、过期窗口及其他动作。

### 响应结束

- ✅ 所有合格玩家完成选择时立即裁决；开启 timeout 时，到期未提交者默认过。关闭 timeout 时必须逐一手动选择。
- ✅ 有人已提交胡时，即使其他人等到超时，也保留已提交的胡。
- ✅ 一炮多响开启时全部胡牌声明生效，关闭时只保留沿加杠者下家方向距离最近的赢家。
- ✅ 真正抢杠胡时，保留原碰组，按预先确定的 `tile_id` 移走被抢的那一张牌，不补摸；由加杠者向赢家付款，胡牌方式记录为“抢杠”。普通模式进入结算并结束本局，不恢复 t3。
- ✅ 所有人过时才完成加杠、补摸一张，并恢复原 t3 剩余时间；这条分支不重新赠送完整 t3。

示例：t3 共 20 秒，用掉 2 秒时进入 t4，则暂停时剩余 18 秒。无论 t4 等待多久，若最后全部过，补牌后仍剩 18 秒；若有人胡，本局直接结算。

调用入口：

```python
game.submit_rob_kong_response(
    player_id, ActionType.HU, now=current_time, source_window_id=window_id,
)
```

`expire_timers(now)` 同样处理 t4。公开快照只为合格玩家返回 `rob_kong_window`；加杠者本人可读取自己的 `paused_turn_remaining_seconds`。

## 信息隐藏规则

### ✅ 倒计时归属

- t3 倒计时只返回给当前行动者。
- t2 倒计时只返回给吃牌选择者。
- t1 只为仍需显示响应选项的玩家返回其窗口计时；出牌者和静默过牌者看不到该倒计时。
- t4 只为具备抢杠资格的玩家返回其窗口计时；加杠者只能看自己的暂停剩余时间。
- `active_timer`、响应窗口、吃牌细节和 t4 快照都会过滤不属于观看者的计时字段；即使调试时公开手牌，也不公开别人的 deadline。

响应窗口尤其要注意信息隐藏。

### ✅ t1 开启

- 只有真实选择时才显示操作。
- 只有 `PASS` 的玩家静默空过。
- 三家都只有 `PASS` 时，不显示响应按钮，但仍等待完整 t1。
- UI 可以显示“等待其他玩家响应”，但不应显示谁只有过。

### ✅ t1 关闭

- 这是慢速/调试模式。
- 所有人都必须明确点击，包括只有 `PASS` 的玩家。
- 该模式不以信息隐藏为第一优先级，而以人工确认和可观察流程为优先。
