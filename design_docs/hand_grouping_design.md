# 手牌分组与动作选牌设计

本文档定义玩家手牌的自定义分组、界面排列，以及执行吃、碰、杠时如何确定要从手牌中移除哪些具体牌。

分组只用于玩家整理手牌和表达选牌意图，不改变手牌的规则含义。判胡、听牌和计番仍然把所有未副露的手牌作为一份完整手牌处理。

## 设计目标

- ✅ 玩家可以把准备组成算式或传统牌型的牌临时放成一组。（状态、接口与单人试牌 UI 已实现）
- ✅ 分组不能让系统获得新的规则信息，也不能影响胡牌结果。
- ✅ 同值牌也必须能区分，玩家点了哪一张，动作就使用哪一张。（Board State 与出牌已支持）
- ✅ 玩家没有明确选牌时，系统按照稳定、可预测的规则自动选择具体牌。
- ✅ 吃、碰、杠执行后，只清理实际被使用的牌；未被使用的分组成员继续留在原组。

## ✅ 稳定牌身份

每一张实体手牌都必须有独立且稳定的 `tile_id`，不能只依赖牌值或当前数组下标。

建议的逻辑结构：

```text
HandTile
  tile_id: str
  value: int | str
```

例如两张牌值相同的 `3`，也可能是：

```text
{ tile_id: "tile-17", value: 3 }
{ tile_id: "tile-42", value: 3 }
```

拖动、分组、拆组不会改变 `tile_id`。数组下标只是当前画面中的位置，不能作为长期身份。玩家主动出牌或 Action 执行器确定吃碰杠所用实体牌时，都必须使用 `tile_id`。

## ✅ 分组数据

每位玩家维护自己的手牌分组：

```text
HandGroup
  group_id: str
  tile_ids: list[str]
  created_order: int
```

约束：

- 一张手牌最多属于一个分组。
- 分组中的每张牌必须仍在该玩家手牌中。
- 分组内 `tile_ids` 的顺序就是画面从左到右的顺序。
- `created_order` 决定组与组之间从左到右的顺序。
- 第一组位于最左边，第二组位于第一组右边，依此类推。
- 第一版不需要允许玩家调整组的左右顺序；以后可以增加整组拖动。
- 摸到的新牌默认不属于任何组，并放在散牌区最右边。

## ✅ 手牌界面布局（状态布局与单人试牌 UI 已实现）

玩家自己的手牌区域按以下顺序排列：

```text
[吃碰杠副露] [第一组] [第二组] ... [散牌]
```

这些区域含义不同：

- `吃碰杠副露`：已经执行并公开的牌组，不再属于手牌分组。
- `第一组、第二组……`：玩家自行整理的暗手牌，规则上仍属于普通手牌。
- `散牌`：尚未加入任何自定义分组的暗手牌。

自定义分组只对该玩家本人可见。其他玩家的状态快照不能暴露分组、选择状态或组内排列。

### ✅ 散牌作为虚拟特殊组

散牌区在逻辑上可以视为一个特殊组，但不应创建普通 `HandGroup`。建议统一表示为：

```text
普通分组目标: group_id = 实际 group_id
散牌区目标: group_id = None
```

这样同一个移动接口可以支持：

- 散牌区内部排序。
- 普通组内部排序。
- 散牌拖入普通组。
- 普通组拖回散牌区。
- 从一个普通组拖到另一个普通组。

散牌区永远位于所有普通分组右边。第一版仍不支持拖动整个分组改变组间顺序；只支持拖动具体实体牌。

## ✅ 鼠标交互（Board State 与单人桌面试牌 UI 已实现）

### 左键

左键承担正常牌局操作：

- 左键点击一张牌，将它标记为当前准备打出的牌并高亮。
- 玩家点击“出牌”按钮后，才提交 `DISCARD` 和该牌的 `tile_id`。
- 左键可以选择分组中的牌，也可以选择散牌。
- 吃牌进入手动选牌模式时，也使用左键选择动作所需的具体牌。
- 拖动牌属于左键操作。

仅有左键高亮不算已经提交动作。玩家必须点击对应确认按钮；如果 t3 超时，未确认的左键选择不覆盖默认超时弃牌规则。

### 右键选择与分组

右键用于切换牌的“待分组选择”状态：

1. 右键点击一张手牌，将它加入当前选择并高亮。
2. 再次右键点击已经高亮的牌，取消选择。
3. 当前选择非空时，UI 显示“分组”命令。
4. 玩家确认分组后，按这些牌确认前的相对顺序创建一个新组。
5. 新组放在已有分组的右边、散牌区的左边。
6. 创建完成后清空临时选择和高亮。

玩家可以选择散牌，也可以选择已有组中的部分牌重新组织。若从已有组取走部分成员，原组保留剩余成员；原组变空时自动删除。

### ✅ 拖动与分组成员变更（Board State 与单人桌面试牌 UI 已实现）

玩家可以直接拖动具体实体牌：

- 拖到某个组内部的指定位置：加入该组，并按落点决定组内顺序。
- 从一个组拖到另一个组：从原组移除并加入目标组。
- 从组中拖到散牌区：取消该牌的组归属，并插入散牌区指定位置。
- 在同一区域内拖动：只改变该区域内部顺序。

如果原组被拖空，系统自动删除原组。拖动只改变手牌布局，不消耗游戏 action，也不刷新 t3。

### ✅ 单牌组与空组

允许一个 `HandGroup` 只有一张牌。这样玩家可以先创建一个占位组，再逐步把其他牌拖入。

单牌组遵循以下规则：

- 最后一张牌被拖到其他组或散牌区后，原组自动删除。
- 最后一张牌被打出或被吃碰杠消耗后，原组自动删除。
- 删除空组后，后续组向左补位，但已有组的 `group_id` 不变。
- 把一张散牌拖到两组之间不会自动创建单牌组；新组只能通过右键选择并确认“分组”来创建。

服务端状态中不允许长期保存空 `HandGroup`。任何移动、出牌或动作执行完成后都应统一清理空组。

### ✅ 拖放命中区域与插入槽（单人桌面试牌 UI 已实现）

UI 负责把鼠标像素位置转换为明确的目标区域和插入位置。服务端不根据坐标猜测玩家想放入哪个组。

每个普通组和散牌区都提供插入槽。例如一个三张牌的组有四个落点：

```text
| 牌 1 | 牌 2 | 牌 3 |
^      ^      ^      ^
0      1      2      3
```

拖到 `target_index = 1` 表示插入牌 1 和牌 2 之间。拖动过程中 UI 必须同时显示：

- 目标普通组或散牌区高亮。
- 具体插入位置的竖线。
- 松开鼠标后牌将进入的区域。

这样玩家在提交前就能看到系统判定，不会等松开后才发现牌进入了错误分组。

### ✅ 两组之间的间隙判定（单人桌面试牌 UI 已实现）

拖到两个区域之间时，间隙按水平方向分成左右两半：

```text
[左边组] [间隙左半 | 间隙右半] [右边组]
```

- 落在间隙左半：加入左边组最右侧。
- 落在间隙右半：加入右边组最左侧。
- 最后一个普通组与散牌区之间同理：左半加入最后一个组，右半进入散牌区最左侧。
- 副露区不能成为暗手牌拖动目标；副露区与第一组之间的无效区域不会把牌加入副露。
- 当前没有普通组时，暗手牌区域的有效落点全部属于散牌区。

组容器应包含少量内部留白作为自己的命中区域；只有真正位于两个容器之间的 gutter 才使用左右半判定。

第一版不支持把牌拖到组间隙后自动创建新组，也不支持拖动整个组改变组间顺序。

### ✅ 原子移动与无效落点

一次跨组移动必须是原子操作：先完整验证，再修改任何状态。

建议请求格式：

```text
MoveHandTileRequest
  player_id
  tile_id
  target_group_id: str | None
  target_index: int
  turn_window_id: str
```

其中 `target_group_id = None` 表示散牌区。服务端按以下顺序处理：

1. 验证当前仍是请求指定的 t3 窗口。
2. 验证该玩家在当前 phase 可以整理手牌。
3. 验证 `tile_id` 仍属于该玩家。
4. 验证目标组仍存在，或目标明确为散牌区。
5. 假设先从原区域移除该牌，再验证 `target_index` 是否在目标区域允许范围内。
6. 全部验证成功后，一次性提交“从原区域移除并插入目标区域”。
7. 清理被拖空的原组并记录仅该玩家可见的整理事件。

以下情况一律取消拖动并保持原状态完全不变：

- 鼠标松开在副露区、按钮区或暗手牌区域外。
- t3 已经结束，客户端仍提交旧窗口的拖动。
- 目标组在拖动期间被删除或改变。
- `target_index` 越界。
- 请求中的牌已经不在手牌中。

UI 遇到无效落点时保留拖动前的位置和原分组。当前 Board State 已补上“验证失败绝不产生部分修改”的原子保证；单人小样使用原生拖放，无自定义回弹动画。

### ✅ 拆除分组（Board State 与单人试牌 UI 已实现）

当光标位于某个分组区域内时，UI 提供“拆组”命令。确认后：

- 删除该 `HandGroup`。
- 牌本身仍然留在手牌中。
- 第一版暂定这些牌保持组内顺序，回到散牌区最左侧。
- 组后面的其他分组向左补位，但 `group_id` 不变。
- 清除这些牌尚未确认的右键待分组高亮；已经完成的手牌顺序不回滚。
- 如果拆组请求发生在 t1、t2、t4 或过期 t3 窗口，拒绝请求并保持原组不变。（阶段与过期窗口校验均已实现）

## ✅ Phase 与整理权限（Phase、整理请求窗口校验与单人试牌 UI 已实现）

只有 `WAITING_TURN_ACTION / t3` 允许整理手牌：

- 当前行动玩家可以分组、拆组和拖动。
- 其他三位玩家也可以同时整理自己的手牌。
- 玩家可以从自己已有的任何分组或散牌中出牌。
- 整理操作不消耗 action，也不刷新 t3。

进入 `WAITING_RESPONSE / t1`、`WAITING_ACTION_DETAIL / t2` 或 `WAITING_ROB_KONG / t4` 后：

- 不允许创建、拆除或修改分组。
- 不允许继续拖动改变手牌布局。
- 已经确认的分组和已经完成的手牌顺序继续保留。
- 所有尚未确认的右键待分组选择取消高亮，不创建新组。
- 待分组牌只恢复普通显示；此前已经完成的拖动和顺序变化不回滚。

右键待分组选择属于 UI 临时状态，不写入 GameState。它应绑定当前 `TURN_DECISION` 窗口；当前 t3 因出牌、胡牌、杠或 timeout 结束时清空。暗杠或加杠补摸后会创建一个新的 t3，因此旧 t3 的待分组选择也要清空。

✅ 自摸使用本次摸牌的稳定 `tile_id`，不依赖拖动后的手牌最右位置。自定义分组不会改变最终胡牌计算；普通模式胡牌后进入结算并冻结本局手牌整理，直到手动开始下一局。

✅ 加杠存在抢杠资格者时，t4 开始前只确定待用实体牌，不立即移除或改变分组。有人抢杠胡时只移走被抢的那一张牌，原碰组保留；全部过才正式升级加杠。t4 期间所有玩家的手牌整理均冻结。

## ✅ 动作中的玩家主动选牌（吃牌手动模式）

吃牌在手动选牌模式下会消耗玩家明确点击的具体实体牌。动作请求应允许携带：

```text
selected_tile_ids: list[str]
```

只要吃牌请求明确提交了具体牌，系统首先验证：

- 这些 `tile_id` 当前都属于该玩家手牌。
- 没有重复选择同一张实体牌。
- 数量和牌值满足所选吃、碰或杠方案。
- 当前 phase、响应来源和动作类型合法。

验证通过后必须使用玩家选择的这些牌，不再执行自动选牌。验证失败时不修改手牌，并直接将本次吃牌视为 `PASS`，不在同一个 t2 内重新选择。

玩家主动选择可以跨越散牌和多个分组。动作完成后，系统按 `tile_id` 从对应位置删除牌，并清理空组。

碰和明杠不提供具体实体牌的手动选择，因为它们只有一种牌值组合；系统直接使用下文优先级 2 至 4 自动确定实体牌。暗杠由玩家选择“杠哪个牌值”后使用同一完整优先级。加杠由玩家选择“升级哪个已有碰组”后使用下文单独规定的优先级 4 例外规则。

## 未主动选牌时的自动选择优先级

以下规则适用于同一个已经确定的动作方案。例如别人打出 `9`，玩家选择用手中的 `3、+、6` 吃成 `3 + 6 = 9`。这里的“需求牌”是 `[3, "+", 6]`，不包括别人打出的 `9`。

自动选择严格按以下优先级执行。命中某一级后就停止，不再考虑后面的级别。

### 优先级 1：玩家明确选择（只适用于吃牌）

如果吃牌请求包含合法的 `selected_tile_ids`，使用玩家左键选择的具体牌。这一级可以覆盖所有分组自动选择规则。碰和明杠不进入这一级，直接从优先级 2 开始。

### 优先级 2：存在内容完全相同的分组

如果某个分组的牌张数和牌值多重集合与需求牌完全相同，就使用该组中的牌。

示例：

```text
需求牌: [3, "+", 6]
第一组: [1, "+", 2]
第二组: [3, "+", 6]
```

系统使用第二组。若有多个完全相同的候选组，使用画面上最左边的候选组。

完全匹配组的全部牌被动作取走后，该空组自动删除，后续分组向左补位。

牌值比较采用多重集合，不能只判断“是否出现过”。例如需求 `[3, 3, 3]` 必须在组中找到三张不同 `tile_id` 的 `3`。

碰和明杠使用相同规则：

- 碰需要三张自己的同值牌；若某组恰好只有这三张牌，优先使用该组。
- 明杠需要四张自己的同值牌；若某组恰好只有这四张牌，优先使用该组。
- 多个组都完全匹配时，使用画面最左边的候选组。

### 优先级 3：某个分组完整包含需求牌

如果没有内容完全相同的组，但一个或多个分组完整包含需求牌以及额外牌，则选择画面上最左边的合格分组，并且需要的牌全部从这一个组中取得。

示例：

```text
需求牌: [3, "+", 6]
第一组: [1, 3, "+", 6, 9]
第二组: [3, "+", 6, "×"]
```

系统从第一组移除 `3、+、6`。在同一组有多张同值候选牌时，按组内从左到右选择最左边的对应牌。第一组剩余 `[1, 9]`，不会因为动作而自动拆组。

碰和明杠同理：如果没有完全匹配组，但某个组至少包含所需数量的同值牌，则使用最左边的合格组，并在该组内从左向右取牌。组内额外牌继续留在原组，分组本身不拆除。

### 优先级 4：没有任何单组完整包含需求牌

如果没有分组，或者没有任何一个分组能够独自提供全部需求牌，则允许从不同区域拼出需求牌：

1. 先扫描散牌区，从左到右取能够满足需求的牌。
2. 仍有缺少时，按第一组、第二组……的顺序扫描分组。
3. 每个组内部都从左到右取牌。
4. 已经满足全部需求后立即停止。

因此，这一级的总体搜索顺序是：

```text
散牌从左到右 -> 第一组从左到右 -> 第二组从左到右 -> ...
```

示例：

```text
需求牌: [3, "+", 6]
第一组: [3, 1]
第二组: [6, 8]
散牌: [2, "+", 3]
```

系统先从散牌取得 `+` 和最左边的 `3`，然后从第二组取得 `6`。第一组中的 `3` 不会被使用，因为需求中的 `3` 已经由散牌满足。

### 加杠例外：直接执行优先级 4

加杠只需要从手牌取出一张与目标碰组同值的牌。它不尝试玩家主动实体选牌、完全匹配组或完整包含组，而是直接按优先级 4 扫描：

1. 如果散牌区有同值牌，使用散牌区最左边的一张。
2. 如果散牌区没有同值牌，按第一组、第二组……扫描。
3. 使用最左边可提供该牌的分组中，组内最左边的同值牌。

因此，即使某个单牌分组与需求牌“完全匹配”，只要散牌区仍有同值牌，加杠也必须先使用散牌。

## 各动作如何使用该规则

- `CHI`：需求牌是吃牌方案中来自自己手牌的全部牌；别人打出的牌不参与手牌选取。
- `PENG`：需求牌是碰牌所需的三张同值手牌，不提供手动实体选牌。
- `MING_GANG`：需求牌是明杠所需的四张同值手牌；别人打出的牌不参与手牌选取，也不提供手动实体选牌。
- `AN_GANG`：需求牌是暗杠所需的全部同值手牌，执行优先级 2、3、4。
- `JIA_GANG`：需求牌是加入已有碰组的那一张同值手牌，跳过优先级 1、2、3，直接执行优先级 4。
- `DISCARD`：始终按玩家点击的具体 `tile_id` 出牌，不走自动选牌优先级。
- `HU`：不执行选牌和移除；自定义分组不传入规则黑箱，不影响胡牌分组方式。

动作所需牌张数由规则判定结果给出，分组选牌器不应自行写死普通麻将的张数。

## ✅ 动作执行后的分组维护

按 `tile_id` 移除牌后：

- 从玩家手牌顺序中删除这些牌。
- 从所属 `HandGroup.tile_ids` 中删除这些牌。
- 组内剩余牌保持原有相对顺序。
- 空组自动删除。
- 非空组继续占据原来的组间位置。
- 散牌中未被使用的牌保持原有相对顺序。

副露的展示顺序和横牌、暗牌方向继续使用 `action_timeout_design.md` 中的规则。自定义分组只决定从手牌中取走哪些实体牌，不决定副露如何展示。

## 服务端职责与 UI 职责

UI 负责：

- 高亮右键选择的牌。
- 渲染副露、各分组和散牌区域。
- 发送创建组、拆组、组内拖动和主动选牌请求。
- 通过 `tile_id` 表达具体牌，不根据牌值自行猜测。

GameState 负责：

- ✅ 保存稳定的手牌身份、顺序和 `HandGroup`。
- ✅ 验证分组中的牌是否真实存在且没有重复归属。
- ✅ 验证玩家主动选择是否合法。（吃牌手动模式）
- ✅ 未主动选择时执行本文的四级自动选择算法。
- ✅ 动作后统一清理手牌和空组。（现有动作执行函数）
- ✅ 对其他玩家隐藏自定义分组信息。

规则黑箱负责：

- 判断某组牌值能否构成合法的吃、碰、杠或胡。
- 返回动作方案需要哪些牌值。
- 不关心 `tile_id`、分组位置、鼠标操作或 UI 排列。

## 建议实现顺序

1. ✅ 为每张手牌增加稳定 `tile_id`，保持现有玩法行为不变。
2. ✅ 增加 `HandGroup` 及创建组、拆组、组内和散牌内排序操作。
3. ✅ 在公开状态快照中只向牌主返回分组和完整手牌排列。
4. ✅ 为移动、建组和拆组增加 t3 window/phase 验证以及失败原子保证。
5. ✅ 为吃牌细节请求增加 `selected_tile_ids`，实现玩家主动选牌验证。
6. ✅ 实现四级自动选择器，让吃、碰、明杠、暗杠使用完整规则，并让加杠直接使用优先级 4。
7. ✅ 正常 Action 执行流程按 `tile_id` 移除并清理分组。（底层 `apply_*` 仍保留按牌值移除的兼容入口供旧测试/脚本使用）
8. ✅ 增加同值牌、重复牌、多组、跨组补牌和动作后空组清理测试。

## 必要测试

- ✅ 同值牌具有不同 `tile_id`，拖动后身份不变。
- ✅ 创建组不会改变判胡输入中的牌值集合。
- ✅ 第一组、第二组和散牌按约定顺序显示。
- ✅ 玩家主动选择能够覆盖所有自动优先级。
- ✅ 多个完全匹配组时使用最左边的组。
- ✅ 没有完全匹配组时，使用最左边的完整包含组。
- ✅ 完整包含组内有重复值时，取组内最左边的实体牌。
- ✅ 没有完整包含组时，先取散牌，再按组从左到右补足。
- ✅ 动作只删除被选中的具体实体牌。（吃、碰、明杠、暗杠、加杠）
- ✅ 组被部分使用后保留剩余牌和顺序。
- ✅ 组被全部使用后自动删除，后续组向左补位。
- ✅ 拆组后牌按原组内顺序进入散牌区。
- ✅ 其他玩家的公开快照不包含该玩家的分组信息。
- ✅ 单牌组最后一张牌跨组移动后自动删除原组的专项测试。
- ✅ 拖到普通组最左、组内、最右位置的插入测试。
- ✅ 普通组与散牌区之间双向拖动的测试。
- ✅ 非法目标组、越界位置和过期 t3 请求不会产生任何部分修改。
- ✅ 拖动使原组消失时，目标位置仍按移除后的布局正确计算。
